# Benchmark Suite

**Per-scenario baseline + iterate** (`baseline.sh` / `measure.sh`) — the
   day-to-day loop. Capture nginx once as a frozen reference, then re-run
   ruxen on every change and watch the delta. Results are persisted in
   `bench/<config-dir>/RESULTS.md` next to the config.

`bench/scenarios/manifest.tsv` is the single source of truth for what each
scenario does (URL, wrk shape, config path, headers). `baseline.sh` and
`measure.sh` read from it.

## Layout

- `bench/<config-dir>/nginx.conf` — one canonical config per dir, parsed by
  both nginx and ruxen (ruxen's silent-ignore allowlist absorbs the nginx
  preamble).
- `bench/<config-dir>/baseline_<scenario>.tsv` — frozen nginx baseline
  (5 runs by default, mean/median/stddev/min/max for req/s, p50, p99).
  Generated by `baseline.sh`.
- `bench/<config-dir>/history_<scenario>.tsv` — append-only ruxen history
  (one row per `measure.sh` run, with commit SHA and dirty flag).
- `bench/<config-dir>/RESULTS.md` — auto-rendered from the two TSVs above;
  do not hand-edit.
- `bench/scenarios/manifest.tsv` — workload matrix.

## Prerequisites

From repo root:

```bash
cargo build --release
```

Required in `PATH`: `wrk`, `curl`, `nginx`; for the HTTP/2 scenarios (`scheme` `h2c` / `h2` in the manifest: `h2c_hello`, `h2c_static_8k`, `h2_tls_hello`), `h2load` (package `nghttp2-client`), which runs them with 10 streams per connection, and a ruxen with HTTP/2 (#144).

Some scenarios need fixtures (the `m19` 1MiB / 128MiB blobs, TLS certs,
htpasswd files). `baseline.sh` / `measure.sh` don't create them — run
`bench/scripts/prepare_fixtures.sh` once first.

Both servers are started with the config's own directory as the prefix
(`-p bench/<config-dir>/`), so relative `root` and `auth_basic_user_file`
paths in the configs work from any checkout location.

## Day-to-day workflow

### 1. Capture nginx baseline (once per scenario)

```bash
bench/scripts/baseline.sh m1_hello                # 5 iterations, default
bench/scripts/baseline.sh m1_hello --runs 10      # more iterations = lower noise
bench/scripts/baseline.sh m1_hello --force        # overwrite existing baseline
```

Each iteration runs the scenario's configured warmup (`5s`) + measurement
(`30s` for most), with a 20s cooldown between iterations. The script writes:

- `bench/<dir>/baseline_<scenario>.tsv` — captured timestamp, run count,
  req/s + p50 + p99 stats, nginx version, kernel, CPU, governor.
- `bench/<dir>/RESULTS.md` — regenerated.

Re-baseline if the host environment changes meaningfully (kernel update,
governor switch, nginx package upgrade) — the baseline file header records
all of these so you can spot drift.

### 2. Measure ruxen on every change

```bash
cargo build --release
bench/scripts/measure.sh m1_hello                          # 1 iteration
bench/scripts/measure.sh m1_hello --runs 3                 # median of 3
bench/scripts/measure.sh m1_hello --note "tried X"         # annotate the row
bench/scripts/measure.sh m1_hello --env "RUXEN_PIN=1"      # env for ruxen
```

Each call appends one row to `bench/<dir>/history_<scenario>.tsv` and
re-renders `RESULTS.md` with Δ vs the nginx baseline median. The commit SHA
is captured automatically; a `*` suffix marks a dirty working tree.

### 3. Read RESULTS.md

Each `bench/<dir>/RESULTS.md` has one section per scenario id served by
that dir (so `m3/RESULTS.md` covers `m3_static_1k` and
`m3_static_1k_low_concurrency`). Each section has:

- **nginx baseline (frozen)** — the reference table.
- **ruxen history** — newest-at-bottom rows showing date, commit, req/s + Δ,
  p50 + Δ, p99 + Δ, non-2xx count, note.

If a measurement regresses unexpectedly, the wrk output for that single
iteration is not retained (only the summary numbers go into the TSV) — re-run
`measure.sh --runs 3` to confirm it's not iteration noise before
investigating.

## Deciding whether a change helps: `pair.sh`

`RESULTS.md` rows are single runs against a baseline captured at another
time. On a machine that also runs the client (and anything else), those
drift by up to ±10%: on the reference laptop the same scenario has read
94.8% and 104.7% of nginx on two evenings, and the CPU boosts for tens of
seconds after idle, so the first run after a pause can read 30–100% high.
They are a log, not a verdict.

To compare two servers or two builds, interleave them:

```bash
bench/scripts/pair.sh static_8k                            # ruxen vs nginx
bench/scripts/pair.sh static_8k --a-bin /tmp/ruxen-main    # this build vs a saved build
bench/scripts/pair.sh m5_conditional_304 --a ruxen \
    --a-env RUXEN_UNSHARE_FILES=0                           # one binary, env toggle
```

First it runs the scenario's generator (manifest column 11) and sends one
request to each side: both must answer 2xx/3xx with the same status, or
nothing is measured. Without that, a checkout that never generated its
fixtures measures 404 against 404 and still prints a ratio (#380).
`--check` stops after this step, which is a cheap way to vet a whole
campaign's scenario list before a long run. The `proxy_ext_*` scenarios
need their backend nginx running (see `bench/proxy_ext/backend.conf`).

Then it runs a 20 s throwaway warm-up of A, then 6 pairs in alternating order
(A B, B A, …), each with the scenario's warmup before a 10 s measurement.
It prints every pair and the **geometric mean of B/A**. Runs that saw any
error response or wrk timeout make it exit 1, because their ratio means
nothing.

Practical rules:

- **Calibrate first.** Run A/A on an identical binary
  (`pair.sh m1_hello --a-bin <copy of target/release/ruxen>`). The spread
  you see is your noise floor. On the idle reference laptop it was about ±1%
  per pair; with a browser and an editor busy, ±5–10%.
- **Keep the number of pairs even.** The second run of a pair reads a few
  percent differently, and equal counts of "A first" and "B first" cancel
  that in the mean.
- **Idle machine, no compiles.** Don't run `cargo build` or the
  nginx-tests sweep at the same time; nginx-tests also uses ports 808x.
- Save the old build before you rebuild:
  `cp target/release/ruxen /tmp/ruxen-main`.

### When the server isn't the bottleneck: `cpu_per_request.sh`

On the no-keepalive scenarios neither server saturates the CPU (wrk and the
kernel's TCP setup are the limit), so req/s barely moves when ruxen gets
cheaper or more expensive. Compare server CPU per request instead:

```bash
bench/scripts/cpu_per_request.sh m1_no_keepalive --server nginx
bench/scripts/cpu_per_request.sh m1_no_keepalive --server ruxen
bench/scripts/cpu_per_request.sh m1_no_keepalive --bin /tmp/ruxen-main
```

It reads the server's utime/stime from `/proc` around one measured run and
prints user/system µs per request. Alternate the runs and repeat a few
times; the first run after idle is unreliable here too.

### Idle connections: `idle_cpu.sh`

What the server spends while nothing happens: N keep-alive connections
each make one request and then stay open, and the server's utime/stime
are read over a window (default 10 000 connections, 10 s). nginx spends
nothing here; a timer or tick per connection or per worker shows up.

```bash
ulimit -n 65536
bench/scripts/idle_cpu.sh m1_hello --server nginx
bench/scripts/idle_cpu.sh m1_hello --bin /tmp/ruxen-main --connections 5000 --seconds 5
```

It prints the share of one core. Plain-HTTP scenarios only; the scenario's
`keepalive_timeout` has to outlast the window.

### Profiling

`perf record -g -p <pid>` works once
`sudo sysctl -w kernel.perf_event_paranoid=1 kernel.kptr_restrict=0` is set
(it resets on reboot). System-wide `-a` stays blocked at that level, so
profile nginx by its worker pids. Distribution nginx packages usually ship
without symbols, so compare nginx at the kernel-symbol level. For ruxen
user-space call stacks, build with frame pointers into a separate target
dir:

```bash
CARGO_TARGET_DIR=/tmp/ruxen-prof CARGO_PROFILE_RELEASE_DEBUG=line-tables-only \
    RUSTFLAGS="-C force-frame-pointers=yes" cargo build --release
```

### Other hardware (#14)

`.github/workflows/bench-hardware.yml` (Actions → "Bench on hosted
hardware" → Run workflow) runs the A/A calibration and `pair.sh` against
nginx 1.30.6, built with the reference configure line, on GitHub's
x86_64 and ARM64 runners. It records the CPU, kernel and the driver
(io_uring or epoll), and uploads the outputs as artifacts. The scenario
list and the number of pairs are inputs.

First data set, 2026-10-28, main `1e716b79` ([#14 comment](https://github.com/gvozdetsky/ruxen/issues/14#issuecomment-6474759301)):
4-vCPU Azure VMs, kernel 7.0 (azure), wrk on the same VM, io_uring.
Geometric mean of ruxen / nginx over 6 pairs:

| scenario | x86_64 AMD EPYC 9V74 | ARM64 Neoverse-N2 | i9 laptop (c021) |
|---|---:|---:|---:|
| A/A m1_hello | 100.1% | 99.9% | 99.8% |
| m1_hello | 115.0% | 120.1% | 102.2% |
| m3_static_1k | 132.5% | 142.9% | 105.0% |
| static_8k | 113.0% | 115.4% | 100.9% |
| m5_conditional_304 | 118.1% | 130.5% | |
| m1_no_keepalive | 96.3% | 92.4% | 95.7% |
| proxy_hello | 113.9% | 130.4% | 97.2% |
| tls_hello | 128.6% | 129.8% | 108.8% |

The A/A spread is about ±1% per pair on these VMs, as on the idle laptop.
The keep-alive lead is much larger than on the laptop: on 4 shared vCPUs the
server and wrk compete for the cores, and on a virtualised kernel io_uring's
fewer syscalls pay off more. `m1_no_keepalive` stays below nginx everywhere.
Missing so far: a client on a separate machine over a real NIC.

## Adding a new scenario

Append a line to `bench/scenarios/manifest.tsv`:

```
id|description|port|path|threads|connections|duration|warmup|cooldown|nginx_config|prepare_script|header_mode|headers|scheme
```

Field notes:

- `header_mode`: `none`, `static`, `etag`, or `last_modified`.
  - `static` reads `headers` as `Header: v;Header2: v2`.
  - `etag` fetches the live ETag and sends it as `If-None-Match`.
  - `last_modified` fetches the live `Last-Modified` and sends it as
    `If-Modified-Since` (so the 304 path works regardless of checkout mtime).
- `prepare_script` is optional and documents which fixture generator the
  scenario needs; `prepare_fixtures.sh` runs all of them.
- `scheme` defaults to `http`; set to `https` for TLS scenarios.
- Multiple scenarios can share a `nginx_config` (e.g. `m3` has two, `m5`
  has five) — they'll appear as separate sections in the same `RESULTS.md`.

After adding, run `baseline.sh <new_id>` to capture the reference.
