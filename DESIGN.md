# ruxen — design notes

Working document: what ruxen decided, why, and what reading the nginx C source taught. It describes the code as it is on `main`; `README.md` has the feature list, and the history of each change is in its pull request.

## Philosophy

**Design-faithful, implementation-idiomatic.** Read the C to understand *why* nginx does what it does (phases, event loop, request state machine, output chains), then write Rust that captures the intent — not the mechanics.

We are not doing:

- **Pure 1:1 port.** nginx's memory pools, ref-counting, and function-pointer module arrays exist largely because C has no RAII, no ownership, no traits. Porting them verbatim fights the borrow checker to recreate problems Rust already solved.
- **Incremental FFI.** Replacing C modules one at a time via bindgen would bury us in `unsafe` and ABI glue before we learn anything about nginx itself.

## Scope

- Linux only (x86_64, aarch64).
- HTTP/1.1 with a hand-written parser, and HTTP/2 for clients through the `h2` crate (#144). No HTTP/2 or HTTPS to upstreams yet.
- TLS termination via rustls, server side.
- **Thread-per-core** workers, each with its own `SO_REUSEPORT` listening sockets, as nginx's worker processes.
- No dynamic modules: what nginx does in modules is compiled in, and an unknown directive fails at startup (see the unknown-directive policy below).
- **Zero-alloc request parsing and prebuilt `return` path.** Static-file responses still build a per-request header `Vec<u8>`; with `sendfile on` the body itself is sent zero-copy (see "Static file bodies and `sendfile`").

## Performance contract

**ruxen must serve every bench scenario at ≥ 95% of the throughput of nginx's current stable release (1.30, measured against 1.30.6) on the same hardware, with zero errors.**

**Reference version.** Since 0.2.1 (decided 2026-10-21) ruxen is a drop-in replacement for nginx's current stable branch, 1.30, not for 1.24.0. Where 1.30 behaves differently from 1.24, that is a compatibility gap with an issue: #582 (upstream defaults), #584, #585, #586, #589, #590, #601, #609. On the bench configs, which set the upstream protocol, the two run at the same speed (±1.3%, `bench/campaign-2026-10-21`). The one exception is a `proxy_pass` to an address without `keepalive`: there 1.30's HTTP/1.1 default exhausts the proxy's own ports (#582). The frozen baselines in `bench/*/RESULTS.md` and the notes written before that date measure and cite 1.24.0.

The scenarios are in `bench/scenarios/manifest.tsv`, with nginx's frozen baselines next to each config (for the minimal `return 200` config, [`bench/m1/RESULTS.md`](bench/m1/RESULTS.md)). A change to the hot path is measured before it merges, as ABBA pairs against the build before it on a quiet machine (`bench/README.md`); a regression is fixed, not shipped. The scenarios still below the line have issues (`performance` label).

**What holds up a release** (since 2026-10-26, `ROADMAP.md`, "How work is chosen"): no regression against the previous release on the headline scenarios (`m1_hello`, `m3_static_1k`, `proxy_hello`, `proxy_64k`, `tls_hello`, `h2c_hello`, `h2_tls_hello`, `gzip_html_8k`). The ≥ 95% line on every scenario stays the target, but a scenario still below it no longer blocks a release: its issue gets a milestone when a user's workload hits it or the fix is cheap.

## Runtime & I/O

- **monoio** — thread-per-core async runtime, io_uring-native. Rationale: nginx's performance comes from process-per-core + `SO_REUSEPORT` + per-worker accept queues = zero cross-core contention. Tokio's default multi-thread runtime is work-stealing, which has cache-line bouncing that's the exact opposite of what this workload wants. Published benchmarks show monoio/glommio matching or beating nginx on plaintext; tokio+hyper typically lags by 30–50%.
- **io_uring first.** ruxen is Linux-only and is built and measured on io_uring; epoll is the fallback below, not a second design.
- **No hyper.** Strict version. Writing the HTTP/1.1 parser and response path ourselves is the whole point of the project.
- **Runtime choice, re-checked (#272, decided 2026-10-13): stay on monoio.** monoio was picked on day one without a comparison, and it has had no release since 0.2.4 (2024-08), so compio and tokio (one current-thread runtime per core, `SO_REUSEPORT` per worker, not the work-stealing runtime) were measured. A bare keep-alive `return 200` server with the same request loop, ABBA against monoio io_uring on the i7 (keep-alive / no keep-alive): compio io_uring 97.9% / 100.0%, tokio 96.8% / 98.8%, monoio legacy (epoll) 92.1% / 100.3%, compio poll (epoll) 68.3% / 97.3%. The runtimes differ by less than ruxen's own overhead over the bare server (8–15% on the i7). ruxen itself ported to tokio through a shim over monoio's rent-style I/O (`spike/272-tokio*`) ran at 75–80% of monoio ruxen on keep-alive, 97% without; taking the per-request timers off didn't close that, and a native port would rewrite every I/O call. compio's epoll path is too slow for a fallback, and its minor releases break the API. So: monoio stays; the epoll fallback (#215) is monoio's legacy driver, HTTP/2 (#144) can use the `h2` crate through a monoio-compat-style adapter, and the release risk is handled by helping maintain monoio (monoio-rs/monoio#406), else by publishing a fork with master's fixes.
- **epoll where io_uring is unavailable (#215).** `main` picks the driver once, before the workers start: io_uring when `monoio::utils::detect_uring()` succeeds, else monoio's legacy driver (epoll), with one `[notice]` saying why. `RUXEN_DRIVER=epoll|io_uring` forces either. `events { use epoll; }` doesn't choose: configurations written for nginx set it because it is nginx's best method on Linux, the bench configs included. The I/O code is the same on both: monoio dispatches each op to the thread's driver, and on Linux the legacy driver implements every op ruxen uses. Measured on the i7 (ABBA, 8 pairs), epoll against io_uring: `m1_hello` 78.8%, `proxy_hello` 78.3%, `m3_static_1k` 74.5%, `tls_hello` 84.2%, `m1_no_keepalive` 101.0%; against nginx 1.24.0: 93.2%, 91.3%, 102.3%, 114.3%, 95.7%. The bare-server spike lost only 8% on epoll, so most of the gap is ruxen's, not the driver's (#337).
- **Ring size and `RLIMIT_MEMLOCK` (#612).** A worker's ring has 4096 entries. Without `CAP_IPC_LOCK`, Linux 7.0 charges every ring to the user's `RLIMIT_MEMLOCK`, about 0.5 MiB at that size, summed over all of the user's processes. The common 8 MiB limit therefore holds about 16 workers, and with more the start failed with `io_uring_setup() ENOMEM`. Each generation now picks its ring size up front (`ring_entries`): the largest of 4096, 1024 and 256 entries whose rings, counted at 128 bytes per entry, all fit the soft limit, with a `[warn]` when that is less than 4096. Up front because workers that grab the limit first would leave the later ones nothing even at 256. A worker that still gets ENOMEM, because the user's other processes or the rings of retired workers hold part of the limit, tries the smaller sizes, again with a `[warn]`. If no size fits, the worker runs on epoll (monoio's legacy driver) with a `[warn]`, rather than failing the start or the reload (#635): a limit that fits one generation fits only part of the next while the old rings remain, and the kernel charges a little more than the estimate. Every worker has a runtime of its own, so a generation may mix the two. `contrib/systemd` sets `LimitMEMLOCK=128M`. A root master creates the first generation's rings before switching to `user`, with `CAP_IPC_LOCK`; a reload creates its rings after the switch.
- **Ring setup flags: `SINGLE_ISSUER | DEFER_TASKRUN`.** monoio 0.2.4 builds its ring with no setup flags, so the kernel interrupts the worker (task work over `TWA_SIGNAL`, an IPI from another core) for every completion. With `DEFER_TASKRUN` it queues that work and runs it when the worker enters with `IORING_ENTER_GETEVENTS`. monoio does that whenever it parks (`submit_and_wait`, or the timed wait). Its other path, the `submit()` after a round that leaves tasks queued, collects no new completions then, which matters only for a task that keeps waking itself; ruxen has none. `SINGLE_ISSUER` is required with it and holds: each worker builds its runtime on its own thread and is the only submitter. A kernel before 6.1 refuses the flag with EINVAL, and the workers fall back to plain rings. Measured on the i7 (ABBA, 6 pairs, against the flagless ring): `m1_hello` +1.9%, `m1_hello_c4096` +3.7%, `static_8k_c4096` +0.4%; the RES IPIs during a run drop to almost none.
- **No tokio runtime.** monoio has its own TCP and I/O primitives. The `tokio` crate is a dependency without features, for the `AsyncRead` / `AsyncWrite` traits the `h2` crate drives its connection through (see HTTP/2).

## Architectural decisions still in force

- **systemd notifications** (#502, `src/sd_notify.rs`): with `$NOTIFY_SOCKET` set, one datagram per message, no library: `READY=1` once every worker accepts, `RELOADING=1` (with `MONOTONIC_USEC`, for `Type=notify-reload`) and `READY=1` around a reload, `STOPPING=1` on SIGQUIT and SIGTERM. With `$WATCHDOG_USEC`, `main` sends `WATCHDOG=1` every half interval, but only while every worker of the running generation has turned its accept loop since the last look (a per-worker counter bumped in `notice_runtime_events`, which runs at least every `ACCEPT_TICK`). A worker stuck in a busy loop or a blocking call stops the pings, which is logged once at `alert`, and systemd restarts ruxen. nginx has neither: its packaged unit is `Type=forking`, and its master only respawns a worker that exited. `contrib/systemd` uses `Type=notify` and `WatchdogSec=30s`.
- **Graceful shutdown** lives in `worker::RuntimeState` — a shared `AtomicBool` polled between `accept` calls in the accept loop. The per-connection hot path is untouched. On SIGQUIT `main` also shuts down and closes its listening sockets at once (`ListenerSet::close`, #552), as nginx's master and workers call `ngx_close_listening_sockets`: a client that connects during the drain is refused, not queued in a backlog nobody accepts from, and connections already queued are reset. The workers drop their duplicates when they notice the flag; the shutdown fails an accept still in flight, which `accept_failed` doesn't log once the worker is stopping. SIGTERM (fast shutdown) doesn't wait: `main` writes the buffered access-log lines, removes the pid file and unix sockets, and leaves with `_exit` (#525), without exit handlers or destructors, which would run while the workers still do (aws-lc's free the global DRBG a worker's first handshake may seed from). nginx's master exits only after its workers; here leaving ends them.
- **Two path prefixes, as in nginx.** `-p` (the cycle prefix) is applied by `chdir` at startup, so `root`, `alias`, logs, and `pid` resolve against cwd. `include`, `ssl_certificate`, `ssl_certificate_key`, and `auth_basic_user_file` resolve against the main config's directory (nginx's conf prefix, `ngx_conf_full_name(cycle, name, 1)`), recorded by the lexer and applied at parse time. The two differ whenever `-c` points outside `-p`.
- **`Date` on every response, stamped at write time.** Like nginx's `ngx_cached_http_time`, the value is a per-thread cached IMF-fixdate (`src/http_date.rs`, `CLOCK_REALTIME_COARSE`, reformatted once per second). Builders write `Date` right after `Server`, but prebuilt heads are built at config time and their per-worker variant caches are shared, so the worker write path overwrites the 29-byte value in place (`stamp_date`, offset recorded by `scan_response_headers`) just before sending; prebuilt responses are copied into the connection's scratch buffer for that. Cost vs no `Date` in ABBA pairs (2026-10-02): `m1_hello` −1.1%, `add_header_many` −1.2%, 304 unchanged. The proxy drops the upstream's `Date` and sends its own, as nginx does by default.
- **Startup errors are `[emerg]` + exit 1, never a panic.** `worker::prepare` returns `Result`: it is where config meets the filesystem (certificates, `root`/`alias` fds, access/error log files), and `-t` runs it too, like `nginx -t` runs module init. Workers report readiness over a channel once their listeners are bound; `main` waits for all of them, so a failed bind is one `[emerg]` line instead of a panic per worker, and the pid file — which Test::Nginx polls as "started" — appears only after every listener accepts. Before the workers bind, `runtime::claim_addresses` binds each listen address once without `SO_REUSEPORT` and closes it: the workers' own sockets all have `SO_REUSEPORT`, which another process of the same user could join, so without this a second ruxen would start and share the port. nginx binds without `SO_REUSEPORT` unless `reuseport` is set and fails with `EADDRINUSE`; ruxen now does the same, with nginx's five tries 500 ms apart and `still could not bind()` (ngx_open_listening_sockets). `reuseport` addresses are not checked, as nginx shares them too. A missing `root` directory is not a startup error: as in nginx it is a 404 per request (`root` defaults to `html`). ruxen opens the root as its `openat2` anchor at startup when it exists, else in each worker on first use (`PreparedRoot::fd`; fds are per worker, see `unshare(CLONE_FILES)`). Remaining `panic!`s in `prepare` guard parser invariants.
- **`-g` inline directives** are prepended as a synthesized prefix before the config file is tokenized. Matches nginx semantics and reuses the existing parser.
- **`-V` feature claims** list only what is implemented: `--with-…` for the optional modules ruxen has (ssl, realip, stub_status, auth_request, http_v2) and `--without-…` for the default ones it lacks. `Test::Nginx::has_module()` reads them, so each claim opts in to a group of nginx-tests files; a claim ahead of the code would unlock files that fail for the wrong reason. A claim is added in the same change as the implementation.
- **Client timeouts on long-lived per-connection timers.** `client_header_timeout`, `client_body_timeout` and `send_timeout` (nginx's 60 s defaults; http and server scope) bound the first-request wait, the whole request header, each body read and each write — `send_timeout` per partial write, as nginx re-arms its timer after every send, so a slow but steady download isn't cut. The header and the keep-alive waits use the address's default server's values, as in nginx (the header comes before the virtual server is known); `client_body_timeout` and `send_timeout` come from the location the request is routed to, inherited location → server → http (#147): the body's from the location found before it is read (`phase::first_body_limit`), the response's from `ProcessMeta::timeouts`. A `monoio::time::timeout` per operation cost ~3% on `m1_hello` / `proxy_hello` (ABBA): every call is a `Handle::current()`, a timer-wheel insert and a remove. Instead each connection owns two `Sleep`s (`worker::ConnTimers`: io, idle) that are only moved forward, and monoio extends a registered timer to a later deadline without touching the wheel. The keep-alive wait's per-request `sleep`s moved onto them too, which pays for the new checks: 100.3% / 99.5% of the previous build on those scenarios.
- **Idle keep-alive connections are woken, not polled (#127).**
  - Nothing ticks while a connection waits for its next request. The worker keeps the wakers of its idle connections (`IdleMark` slots, thread-local) and wakes them for the three rare events they wait for, as nginx pushes them (`ngx_drain_connections`, `ngx_close_idle_connections`):
    - a `worker_connections` drain, where it is set;
    - shutdown and a reload, which the accept loops notice on every turn. They run at least every 50 ms per worker anyway, which costs two atomic loads.
  - The idle timer is moved only when it fires before the keep-alive deadline (`arm_idle`): a request costs a clock read, not a timer update.
  - `keepalive_min_timeout` (#601): for that long after a response the wait isn't idle yet (`hold_keepalive`, no `IdleMark`), so a shutdown, a reload or a drain leaves it open; a request then is served with `Connection: close`. At its end the connection closes if shutting down, else it waits the rest of `keepalive_timeout` as idle (ngx_http_set_keepalive, ngx_http_keepalive_handler). Off, the wait costs one more branch.
  - Before, each idle connection woke 20 times a second and the wait moved two timers per request. With 1000 idle connections on 4 workers, CPU over 10 s went from 68 to 14 ticks.
- **Request bodies: memory, then a temp file; read before routing.** Bodies are read right after the header, before the location is known, into a `BodySink`: in memory up to the location's `client_body_buffer_size`, then spilled to a temp file as they arrive, so a stalled upload holds no more than nginx's does (#507). One difference: when nothing can tell where the body is (no `$request_body` or `$request_body_file` in the config, no `client_body_in_file_only`, a Content-Length body), a body past the buffer stays in memory while it arrives within 20 ms, up to 256 KiB, and goes to the file only then. The proxy forwards a body in memory without a copy, and a fast 64 KiB POST costs no file (#289). The chunked decoder streams chunk data into the sink and drops consumed input, so memory stays bounded whatever the chunk sizes. Before reading, the request is routed far enough to find the location's `client_max_body_size` (`phase::first_body_limit`, nginx's default 1m; `0` = unlimited), so a Content-Length over it is a 413 without reading the body, as nginx does. The spill files are created `0600` and exclusively, in `client_body_temp_path` (http scope) or a private `0700` directory under `$TMPDIR`. A body in the file has an empty `$request_body` and a `$request_body_file`, as in nginx, and `run_proxy` streams it to the upstream after the header block, reopening the file per attempt so failover re-sends it.
- **`worker_connections` per worker, with idle reuse.** `events { worker_connections N; }` (default 512) caps each worker's connections at N minus the listening sockets, as listeners use slots in nginx. Upstream connections count too, in the pool as well (`UpstreamSlot`), since nginx takes them from the same table; there is no master channel, so a worker has one slot more than nginx's. A new upstream connection without a slot first closes an idle keep-alive one, else the request gets a 500 with the `[alert]` below (ngx_http_upstream_connect); a new client closes an idle keep-alive upstream connection before it is refused. Accounting is thread-local (`WorkerConns`: active / idle / drain) because a worker owns its connections. Like `ngx_drain_connections`, when free slots drop to a sixteenth, up to 32 (an eighth) of the connections waiting for a request are asked to close; they are woken to do so (see "Idle keep-alive connections are woken" above). With no slot left, the new connection is closed and `[alert] N worker_connections are not enough` is logged, at most once a second (the reuse case logs `[warn] …, reusing connections`). Without the reuse, idle sockets could hold every slot until their timeouts.
- **Error-log lines use nginx's layout and context.** `2026/10/02 14:00:00 [error] <pid>#<tid>: *<connection> <message>, client: …, server: …, request: "…", upstream: "…", host: "…"` (`worker::write_error_log`; local time, like `$time_local` and `$time_iso8601`, with the zone's offset from `localtime_r` looked up once a minute per thread, as nginx's ngx_time_update, #614). Failed upstream attempts are logged with nginx's wording (`connect() failed (111: Connection refused) while connecting to upstream`, `upstream timed out … while reading response header from upstream`, `no live upstreams …`): `proxy::run_proxy` appends them as `AttemptFailure`s to a `Vec` the worker passes in, and the worker adds the request context. The happy path allocates and formats nothing; the reason is boxed inside `AttemptOutcome::Failed` because growing that enum (every attempt returns one) cost ~1.5% on `proxy_hello` in ABBA pairs, and so did wrapping the result in a second async layer. `error_log` is inherited like nginx's (location ← server ← http ← top level). With none in scope, lines go to stderr at level `error` (nginx's default is its compiled-in `logs/error.log`; ruxen runs in the foreground and `-e` redirects stderr). `syslog:` targets send nginx's RFC 3164 datagrams (`src/syslog.rs`), for `access_log` too.
- **access_log files are opened once per path, in `prepare`** (#523), as nginx's master opens `cycle->open_files` (`ngx_init_cycle`): the `File` is kept in the configuration's arena, and each worker writes to a `dup` of it (`open_access_logs`), so a FIFO's reader sees one writer from start to end. SIGUSR1 reopens by path in each worker, one file at a time (#522); the retired configuration's arena closes `main`'s copies.
- **Responses say ruxen; the test harness gets nginx.** `Server` and the built-in error pages' footer carry `ruxen/<version>` (`http::identity`). nginx-tests asserts `nginx/<version>` (`server_tokens.t`, error-page bodies), so `scripts/run_nginx_tests.sh` sets `RUXEN_NGINX_IDENTITY=1`, read once at config preparation, never on the request path. The same switch gates `-V`'s `nginx version: nginx/1.30.6` line, which Test::Nginx parses to decide which tests apply: outside the harness a version scanner or inventory tool would take it as a real nginx release. The `configure arguments` list prints in both modes.
- **Unknown-directive policy** is an explicit allowlist, not "accept everything". An unknown directive in a test config almost always means the test exercises a feature we don't implement; silently accepting would produce a wrong-looking pass instead of a clear "not yet" failure. The allowlist is for tuning knobs only: a directive that restricts access and isn't implemented yet (`root` / `alias` with variables were one until #232; `ssl_verify_client on` until #113, `proxy_cookie_flags` until #40) fails closed with an `[emerg]`, because ignoring it would serve what the config says to protect (`config::reject_unenforced`, checked by the lexer for every directive). Warnings only: `ssl_ecdh_curve` (rustls has no weak groups to fall back to). `ssl_ciphers` is evaluated over rustls's TLS 1.2 suites (`tls_ciphers`): a list restricts and orders them as it would OpenSSL's, and one that leaves none offers TLS 1.3 alone (an error when TLS 1.3 is off).
- **Out of scope for nginx-tests interop:** any `.t` that uses `Test::Nginx::Stream`, `Test::Nginx::IMAP`, `Test::Nginx::SMTP`, `Test::Nginx::POP3`; any test whose conf references directives outside the allowlist; any test requiring dynamic-module loading. The full per-file pass/fail/skip taxonomy lives in [`NGINX_TEST_PROGRESS.md`](NGINX_TEST_PROGRESS.md); regenerate it via `scripts/run_nginx_tests.sh --update-progress`.

### Why the nginx-tests track matters

- External validation. The upstream suite encodes corner cases we haven't thought of (method handling, Host edge cases, 404 vs 403 policy, header canonicalization). Passing even a handful of its `.t` files is a stronger correctness signal than any tests we write ourselves.
- Forcing function for CLI and lifecycle surface — real nginx interop required the `-c / -p / -e / -g` handshake, PID files, and signal-driven lifecycle.
- Feeds future planning. Every failing `.t` file is a direct vote for which directive or module to implement next, replacing guesses about what matters.

## Notes from reading the C source

### `src/core/ngx_conf_file.c` — config parser

**Architecture:** tokenizer-driven recursive descent. Two functions do everything.

- `ngx_conf_read_token` (lexer). Reads one directive's worth of whitespace-separated tokens into `cf->args`, returns a **terminator code**: `NGX_OK` (`;`), `NGX_CONF_BLOCK_START` (`{`), `NGX_CONF_BLOCK_DONE` (`}`), `NGX_CONF_FILE_DONE` (EOF).
- `ngx_conf_parse` (loop). Call tokenizer → dispatch `cf->args[0]` via `ngx_conf_handler` → if terminator was `{`, recurse into `ngx_conf_parse` in `parse_block` mode.

**Dispatch is table-driven.** Each module exposes `ngx_command_t[]`: `{ name, type-bitmask, set-fn, conf, offset, post }`. Parser matches on name, validates `type` (allowed arg count *and* allowed context like "only inside `http {}`"), calls the `set` handler. The `offset` field is a pointer-arithmetic substitute for "write this field of the conf struct" — Rust gets this for free.

**Lexer handles:** `#` line comments, `"…"` / `'…'` quoted strings, `\` escape, `$` variable prefix, buffered refills of `b->pos..b->last`.

**Rust mapping:**

- Tokenizer: one directive at a time, its arguments plus a `Terminator` (`;`, `{`, `}`, end of file), instead of the int return code and the `cf->args` side channel.
- Dispatch: a `match` on the directive name in each block's parser (`parse_server`, `parse_location`, …), writing typed fields. Replaces the `ngx_command_t` table, function pointers, and `void *` offsets.
- Config parsing happens at startup and on each reload, and produces an immutable `HttpConfig` tree. No allocation concerns here — the hot path never touches the parser.

### `src/http/ngx_http_parse.c` — request-line & header state machine

**Shape.** One function per thing (`ngx_http_parse_request_line`, `ngx_http_parse_header_line`, `…_uri`, `…_chunked`). Each is a `for (p = b->pos; p < b->last; p++) switch (state)` loop. Compilers lower this to a computed-goto jump table (the comment on line 105 even says so). Each byte costs one table-jump + one comparison.

**Resumable by design.** On exhaustion of the buffer the function writes back `b->pos = p; r->state = state; r->header_hash = hash; r->lowcase_index = i` and returns `NGX_AGAIN`. Caller reads more bytes into the same buffer (appends at `b->last`), then re-enters the parser — which picks up exactly where it left off, mid-header, mid-URI, wherever.

**Tricks worth stealing.**
- **`usual[]` bitmap** (line 17): 256-bit table of "benign" URI chars, packed into 8 `uint32_t`s. `usual[ch >> 5] & (1U << (ch & 0x1f))` is a branchless tchar check.
- **`lowcase[]` LUT** in `parse_header_line` (line 875): 256-byte table that returns the lowercased char for valid token chars and `0` for everything else. Validates + normalizes in one lookup.
- **Rolling hash** built per-byte while parsing the name (`hash = ngx_hash(hash, c)`). At header-done, `ngx_hash_find` dispatches to the handler by hash — no strcmp per known header. Combined with `lowcase_header[NGX_HTTP_LC_HEADER_LEN]` (power-of-two ring-buffered lowercase copy) the hash-match is confirmed with one memcmp.
- **`ngx_str3_cmp` / `ngx_str4cmp`** on little-endian + unaligned hosts: the method switch reads 4 bytes as a single `uint32_t` and compares against a packed literal. `"GET "` as `'G' | ('E'<<8) | ('T'<<16) | (' '<<24)` = one load, one `==`.

### `src/http/ngx_http_request.c` — request lifecycle

**Handler chain, not a function.** A "request" isn't a call — it's a sequence of epoll callbacks:

```
accept →
  ngx_http_init_connection  (no buffer yet; sets rev->handler = wait_request_handler)
    wait_request_handler    (only here does c->buffer get allocated; reads first bytes)
      process_request_line  (loops: read → parse_request_line; NGX_AGAIN re-arms epoll)
        process_request_headers  (loops: read → parse_header_line; per-header dispatch)
          process_request   (run 11 phases: rewrite, access, content, …)
            write body / filter chain
              finalize_request → set_keepalive
                (idle)        → keepalive_handler → wait_request_handler (loop)
                (pipelined)   → create_request → process_request_line   (loop)
                (close)       → close_connection
```

**Lazy buffer allocation is the keep-alive memory trick.** `wait_request_handler` only calls `ngx_create_temp_buf` once readable data arrives; `set_keepalive` calls `ngx_pfree(c->pool, b->start)` on transition to idle, and uses `b->pos = NULL` as a sentinel meaning "buffer is gone". Idle keep-alive connections thus hold only the `ngx_connection_t` + `ngx_http_connection_t` + a tiny pool — no 8 KiB read buffer. At 10 k idle keep-alives that's the difference between ~80 MB and ~1 MB.

**Pipelining.** After `set_keepalive`, if `b->pos < b->last` there's a follow-up request already in the buffer — nginx does **not** memmove; it creates a new `ngx_http_request_t` over the remaining bytes in place (`r = ngx_http_create_request(c); r->pipeline = 1;`) and posts the parse directly.

**Header dispatch.** After each header is parsed, nginx does `ngx_hash_find(&cmcf->headers_in_hash, h->hash, lowcase_key, len)` and calls the per-header handler (`ngx_http_process_connection`, `ngx_http_process_host`, …) which writes into `r->headers_in` struct fields.

**`post_action` runs after the main response and suppresses its own output.** `ngx_http_finalize_request` calls `ngx_http_post_action` after the main request is done but before keep-alive finalization. The helper reads the effective core location config's `post_action`, sets `r->http_version = NGX_HTTP_VERSION_9`, `r->header_only = 1`, and `r->post_action = 1`, then internally redirects to a `/uri` target or jumps to a named location. `ngx_http_send_header` returns `NGX_OK` immediately for post-action requests, so the post-action body/header never reaches the client, but the internally redirected request still runs content handlers and reaches access logging.

### `src/core/nginx.c` + `src/os/unix/ngx_process_cycle.c` — process model

Master-worker via `fork()`: `ngx_start_worker_processes` spawns N workers, keeps socketpair channels for control messages (`NGX_CMD_OPEN_CHANNEL`, reload, shutdown). `SO_REUSEPORT` is set per-listen-socket in the workers, same as we do.

We use OS threads, not processes. Consequences:
- Shared address space → `&'static PreparedServer` works, no IPC needed for config.
- **A panic ends a connection, not the server; a dead worker ends the server** (#130, `src/worker/panics.rs`). Each connection future is wrapped in `Contained`, which catches an unwind in `poll`: the connection is dropped (its guards still run, so the counters stay right), an `alert` names the connection, and the worker keeps serving the others. A panic hook writes every panic message, with its location, to the error log at `alert` (stderr too with `RUST_BACKTRACE`). A panic outside a connection ends the worker thread; `main` no longer joins in order but waits on a channel every worker signals when its thread ends, and on a panic stops the other workers as on SIGQUIT, removes the pid file and exits 1. That stop is bounded (#495): `main` shuts its listening sockets down and closes them at once (`ListenerSet::close`), so new connections are refused rather than queued for nobody, and the other workers get `worker_shutdown_timeout`, at most 5 s (`PANIC_STOP_AFTER`; also when none is set), before `force_close` and the backstop end their connections; the point is to hand over to the supervisor. `shutdown(2)`, not only `close`: the panicked worker's io_uring keeps its accept in flight after the thread is gone, and that holds the socket open. For the same reason the dying worker shuts its own connections down before its thread ends (`end_connections_on_panic`), so their clients see the end at once, as when nginx loses a worker process. nginx's master respawns a dead worker in its slot (`ngx_reap_children`); ruxen leaves the restart to the supervisor (`Restart=on-failure` in `contrib/systemd`). `RUXEN_TEST_PANIC=trace|worker|later` forces either case for `tests/m101_worker_panic.rs`. Not `panic = "abort"`: it would make every panic fatal.
- **Reload starts a new generation of worker threads** (#89, `main.rs` `Master::reload`, `src/worker/listeners.rs`). nginx's master re-runs `ngx_init_cycle`, which inherits the listening sockets of the old cycle (`ngx_cycle.c`, `ls[i].remain`), starts new workers and sends the old ones `NGX_SHUTDOWN_SIGNAL`. Here `main` is the master: on SIGHUP (or `-s reload`) it parses and prepares the configuration on a short-lived thread (parsing and preparing keep state in thread locals, which then start empty), opens what the new configuration listens on, starts its workers with a `RuntimeState` of their own, waits for them to be ready, and only then retires the old generation (`begin_shutdown`: stop accepting, close keep-alive connections, finish requests). A failure at any step is logged at `emerg` to the old configuration's error log, and the old generation keeps running, as nginx keeps its old cycle. The listening sockets belong to `main`, not the workers: one `SO_REUSEPORT` socket per address and worker slot, so worker *i* of each generation accepts from the same queue and nothing queued is reset in the handover; a slot or address the new configuration drops is closed once the old workers stopped accepting, which resets what is queued there, as nginx's closing of a listening socket does. A worker accepts on a duplicate and closes the rest of `main`'s listeners in its fd table copy, so a dropped socket really closes. `worker_shutdown_timeout` after a reload: `main` sets `force_close`, and each old worker shuts down (`shutdown(2)`) every connected socket it opened itself, which ends its connections as a closed peer would; descriptors it inherited (stdio, roots, the root helper) are left alone. A connection waiting for its first request is not closed by a shutdown (nginx's `ngx_close_idle_connections` closes only keep-alive ones), so one accepted just before the old worker stopped is served, not reset. What carries over, as nginx keeps a shared zone of the same name and size: `proxy_cache_path` zones declared the same way keep their index and manager (`proxy_cache::zone_for`), and `limit_req` / `limit_conn` zones their buckets and counts (`LimitReqZone::declare`, `LimitConnZone::declare`; another key for a kept zone fails the reload with nginx's message, a new rate applies to the kept state). So does an `ssl_session_cache shared:NAME:SIZE` declared the same way: its sessions and ticket keys (#342). What doesn't: upstream `zone` state and keep-alive pools start fresh; the `-e` / stderr redirection is decided at startup; `user` can't change, and after the switch to `user` the reload reads files as that user, where nginx's master reads them as root (#774); at startup, a `[warn]` names each file the load read as root that the user can't open (`privileges::note_read`, `unreadable_startup_files`). It binds new ports below 1024 as nginx's root master does (#344): `privileges::switch` keeps `CAP_NET_BIND_SERVICE` (`PR_SET_KEEPCAPS`, then `capset` down to that one, permitted only), and `main` makes it effective just around `ListenerSet::open` (`with_bind_capability`). Capabilities are per thread: the workers running at the switch lose all of theirs in setuid, threads `main` starts later inherit it as permitted, which the process's shared memory makes no weaker than any other split. It is what `contrib/systemd` grants an unprivileged ruxen anyway; the root helper binding sockets and passing them back (`SCM_RIGHTS`) would keep it out of the process, at the cost of a protocol the helper must validate. A generation's prepared configuration is built from leaked boxes, since workers and connections hold `&'static` references into it; `arena` records those leaks while `prepare` runs, and `main` frees them once the generation's workers are joined (#343), as nginx destroys an old cycle's pool, and those of a reload that fails (in `prepare`, binding, or starting its workers) at once (#499), as `ngx_init_cycle` destroys a cycle it couldn't finish. The root directories `prepare` opened are closed then too (`PreparedHttp::close_root_fds`).
- **One fd table per worker anyway.** Threads share the process fd table, and every `open`/`close` takes its spinlock (`alloc_fd`, `file_close_fd`). With one open + close per static request on 32 workers, that lock was 5–8% of CPU on the 304 bench (`native_queued_spin_lock_slowpath`); nginx's worker processes never contend on it. Each worker calls `unshare(CLONE_FILES)` first thing, which gives the thread a private copy of the table. That is safe because no fd crosses threads after startup (root-dir fds, stdio and the listening sockets are opened before the workers spawn and get copied; the io_uring ring, connections, per-request files, and access-log handles are opened by the worker that uses them). Measured with ABBA pairs on one binary (`RUXEN_UNSHARE_FILES=0` restores the shared table): 304 +4.7%, 1 KiB static +3.6%, `return 200` unchanged. `tests/m46_worker_fd_table.rs` checks it via `/proc/<pid>/task/*/fd`. Docker's default seccomp profile allows `unshare` only with `CAP_SYS_ADMIN`, so `contrib/docker/seccomp-io_uring.json` allows it with `CLONE_FILES` alone (`SCMP_CMP_EQ 0x400`), which opens no namespace (#274); systemd's `RestrictNamespaces=` and `~@privileged` let it through as is. If it fails anyway, ruxen says so once and the workers share the table.
- **`stub_status` counters are per worker** (#96, `src/worker/stats.rs`). nginx keeps them as atomics in shared memory, which every worker updates on every request. Here each worker owns a cache-line slot, is its only writer, and updates it with a relaxed load and store (no locked instruction); `stub_status` and `$connections_*` sum the slots. The counters are kept only when the configuration has `stub_status` or a `$connections_*` variable; otherwise `ConnStats` is inert and the accept loop skips them. States as nginx counts them: waiting from accept or the end of a response until the next request's first bytes, reading until its head is parsed, writing until its response is done. A TLS handshake isn't counted yet: the connection enters `handle` after it.
- **`ruxen_metrics` counters are per worker and per generation** (#481, `src/worker/metrics.rs`, `docs/metrics.md`). Prepare gives each server block (per listen address) and upstream peer a slot index, only when some location has `ruxen_metrics` (`PreparedHttp::metrics`); otherwise the update sites (response done in `handle`, an upstream attempt in `proxy::run_proxy`, `upstream::report_failure`) see `None` and do nothing else. Each worker allocates its slots when it starts, cache-line aligned, and is their only writer (relaxed load and store); the handler sums them. The slots belong to the configuration, so a reload starts them at zero, and the arena frees them with it. `limit_req`, `limit_conn` and cache zones keep their counts across a reload, as their state (`metrics::ZoneCounters`, kept with the zone): those outlive the workers, so a slot per thread number (64, wrapping) updated with a relaxed `fetch_add`, uncontended in practice; they count whether or not metrics are shown, on paths that already take the zone's locks.
- **`listen unix:` is bound once, by `main`** (#263). A unix stream socket can't be shared with `SO_REUSEPORT`, so `main` binds it before the workers start (`listeners::bind_unix`: a socket file left behind fails with EADDRINUSE, the socket is made 0666, as `ngx_open_listening_sockets` does), and each worker accepts on its copy of the descriptor in its unshared fd table, as nginx's workers share the inherited socket. A connection is carried as a `TcpStream` (recv/send on the descriptor, as for `unix:` upstreams), and the listen marks its peer as `unix:`: `$remote_addr` is `unix:`, `$remote_port` empty, and only `all` / `unix:` rules of `allow` / `deny` and `set_real_ip_from` match it. The socket file is removed when ruxen exits.
- **`limit_req` zones are shared by the worker threads** (#94, `src/worker/limit_req.rs`). nginx keeps a zone in shared memory behind one mutex; here a zone is a heap value every worker reaches through `&'static`, in 64 shards by key hash, each a `Mutex` around a hash map and an LRU list, so workers only wait for each other on the same shard. A per-worker bucket would hand a client with N connections N times the rate, so the zone has to be shared. Capacity comes from the configured size (an entry per 128 bytes) and is fixed: a full shard evicts like `ngx_http_limit_req_expire`, nothing grows. The arithmetic is nginx's, in thousandths of a request, on a process-wide millisecond clock. The check runs in the pre-access place (after the rewrite phase and realip, before allow/deny), once per request. A delay stops processing before the content handler: the worker sleeps, then processes the request again past limit_req (`limit_req::resume_after_delay`), so the handler, the upstream and `$request_time` come after the delay, as nginx resumes its phases. Unlike nginx, the client connection isn't watched during the delay. `limit_conn` (#95, `src/worker/limit_conn.rs`) uses zones of the same shape (a count per key; a key goes when its count does). A request that passes holds its counts in a `limit_conn::Held` guard carried by `ProcessMeta` (in an `Rc`, as the meta is cloned), which lives until the response is written and logged, and through an X-Accel-Redirect; dropping it gives the counts back, as nginx's request-pool cleanup does. It runs after limit_req, as nginx orders the two handlers. A client that goes away while its proxied request waits for the upstream gives its count back then (#136).

- **`user` switches the whole process** (`src/privileges.rs`). nginx's master stays root and each worker process calls `setgid`, `initgroups`, `setuid` (`ngx_worker_process_init`). Here the workers are threads and glibc applies credential changes to every thread, so the switch is process-wide and final: `main` binds the listening sockets and the workers open their access logs as root, report ready and wait; `main` writes the pid file, hands the log files and `client_body_temp_path` directories to the user (`chown`, as `ngx_reopen_files` / `ngx_create_paths` do), switches, checks with `getresuid`/`getresgid` that all three IDs changed and that `setuid(0)` fails, and only then releases the workers (`RuntimeState::release_workers`). Requests, SIGUSR1 reopens and lazily opened root fds run as the user. Per-thread credentials (raw `setresuid` per worker, main thread root) were rejected: a root thread in the same address space is no boundary. What nginx's master still does as root after startup — recreate log files after logrotate (`ngx_reopen_files`, with `chown` to the user) and remove the pid file from `/run` (`ngx_delete_pidfile`) — a root helper does: a child forked before the workers start, while the process still has one thread (`privileges::start_helper`). It keeps only stdio and a socketpair, ignores the terminal and service signals, and takes one-byte commands: pid file written, reopen logs (it opens each configured log `O_NOFOLLOW`, creates it if missing, and `fchown`s only a regular file with one link, so a user who owns the log directory can't point root at another file), reloaded (#498: it re-reads and parses the configuration itself, as root, and takes the log files from its own parse, `HttpConfig::log_file_paths`, as nginx's master reopens the files of the current cycle), exit. It never takes a path from the server and exits on the socket's EOF, so it dies with the server; the pid file is removed only after the server said it wrote it, so a second instance that fails to bind doesn't remove the first one's. The server stays the main process: the pid file, `MainPID` and the signals are unchanged. Reload (#89) can ask it to bind new privileged ports the same way (`SCM_RIGHTS`).

### `src/http/ngx_http.c` + `ngx_http_core_module.c` — virtual servers, locations, phases

File:line citations in the notes below are against the stock 1.24.0 checkout. Newer ones cite `release-1.30.6`, which the checkout one directory up now tracks.

**Server name match tables are built per-listen-socket.** `ngx_http_server_names` (ngx_http.c:1541–1654) walks every `server_name` directive in every `server {}` under one `listen`, partitions them into four categories by first byte (`ngx_http.c:4486–4523`):

- Exact names → one hash (`hash.hash`)
- `*.foo.com` (wildcard-head) → `wc_head` hash
- `.foo.com` / `foo.*` (wildcard-tail) → `wc_tail` hash
- `~regex` → `regex[]` array

Exact + both wildcard hashes go into an `ngx_hash_combined_t`, looked up in that order by `ngx_hash_find_combined` (ngx_http_request.c:2501–2503). Regex is tried last, linearly (request.c:2512–2568). All names are **lowercased at config time** (`ngx_hash_key_lc`, ngx_http.c:1601), so lookup is pure hash-compare; the incoming Host is lowercased *by the parser* before the hash is finalized (request.c:2251–2253, 2388–2395). No per-request casefolding on the hot path.

**Default server is a per-listen-socket field, not a server_name.** `addr->default_server` (ngx_http.c:1661) is resolved at config merge; picked when every lookup misses. Unknown or missing Host → default server, *not* 404.

**Host validation happens in `ngx_http_validate_host`** (request.c:2210–2404). Port suffix is **stripped before matching** — `*hostp` is returned port-less, `*portp` holds the port separately (request.c:2266, 2397–2401). Trailing dot is peeled (2380–2382). IPv6 literals in `[...]` are allowed. Empty host → `NGX_DECLINED` (2384–2386). Missing Host on HTTP/1.1 = 400 (request.c:2034–2039); HTTP/1.0 is allowed through with empty `server.len`, which also falls to default. Duplicate Host header = 400 (request.c:1873–1881).

**Location matching is a binary search tree, not a trie.** `ngx_http_core_find_static_location` (core_module.c:1494–1570) walks an `ngx_location_tree_node_t` tree keyed on prefix. On an exact `=` hit at the current node (`node->exact`), it returns `NGX_OK` immediately — that's final. Otherwise it tracks "best prefix so far" via `rv = NGX_AGAIN` (line 1531) and keeps descending. Regex locations (if any) are tried after the prefix walk in a linear loop (core_module.c:1454–1478), **unless** the matched prefix was declared `^~` (noregex flag).

**Longest prefix wins via tree depth**, not a separate sort. We use a length-sorted `Vec` because our counts are tiny; the complexity of a location tree only pays off past a few dozen locations.

**Phases: 11, enum `ngx_http_phases` in core_module.h:111–129.** Order: POST_READ, SERVER_REWRITE, **FIND_CONFIG**, REWRITE, POST_REWRITE, PREACCESS, ACCESS, POST_ACCESS, PRECONTENT, **CONTENT**, LOG.

- `FIND_CONFIG_PHASE` is **hardcoded** — not registerable like the others. `ngx_http_core_find_config_phase` (core_module.c:970) just calls `ngx_http_core_find_location(r)` inline.
- Every other phase is a list of `ngx_http_phase_handler_t` entries; modules push to `cmcf->phases[i]` at config time, then `ngx_http_init_phase_handlers` linearizes them into one flat `phase_engine.handlers[]` array.
- Each handler has a `checker` (phase semantics) and a `handler` (the actual work). Checker returns `NGX_OK` → next phase (`r->phase_handler = ph->next`), `NGX_DECLINED` → next handler (`r->phase_handler++`), `NGX_AGAIN`/`NGX_DONE` → pause (core_module.c:906–939).
- **`return` is a rewrite-module directive, not a content handler.** It answers in SERVER_REWRITE / REWRITE, so ACCESS (`auth_basic`) never runs for it — `location / { auth_basic "x"; return 200; }` serves 200 without credentials. A `break` ends the rewrite script before a later `return` is reached, so access control does run then. ruxen stores a top-level location `return` as `PreparedHandler::Return` and skips access control for it unless the rewrite program ended on `break`.

**Header dispatch is a real hash, built at startup.** The `ngx_http_headers_in[]` static array (request.c:80–206) pairs name → `offsetof(ngx_http_headers_in_t, field)` + handler. `ngx_http_init` (ngx_http.c:418–446) calls `ngx_hash_init` over this array, case-folding keys. During parsing, the rolling hash `hash = ((hash << 5) + hash) ^ c` is computed byte-by-byte in the sw_name state; at `:` the finished hash + lowercased key + length goes to `ngx_hash_find` (request.c:1540–1541).

**Mapping for ruxen.** Rust's `match` on `(hash, len)` with the lowercased copy confirmed by memcmp is strictly simpler than porting `ngx_hash_t`'s bucket-chain structure — same complexity, none of the pointer arithmetic. A `struct HeadersIn { host: Range, connection_keep_alive: bool, ... }` full of typed fields, populated in `ParseState`, matches nginx's flat-struct `r->headers_in` without the `offsetof` dance.

### `src/http/modules/ngx_http_static_module.c` + `ngx_http_index_module.c` + `ngx_http_try_files_module.c` — filesystem routing

All three are CONTENT-phase (or PRECONTENT, for try_files) handlers that share a single concern: how to map a request URI into a file on disk.

**`ngx_http_static_module.c` — the baseline.** One handler (`ngx_http_static_handler`, 278 LoC) registered on `NGX_HTTP_CONTENT_PHASE`. Flow (static_module.c:49):

- If the URI ends with `/`, return `NGX_DECLINED` (line 67–69). That lets the index module take over. This is the protocol between static and index — not a fallthrough, a two-handler chain.
- Otherwise `ngx_http_map_uri_to_path` builds `<root><uri>` (line 78).
- Open the file via `ngx_open_cached_file`. ENOENT/ENOTDIR/ENAMETOOLONG → 404; EACCES/EMLINK/ELOOP → 403; other errors → 500 (line 106–134).
- If the opened entity is a *directory* (URI without trailing slash), emit `301 Moved Permanently` with `Location: <uri>/?<args>` (line 148–204). Args are preserved; URI is re-escaped if it contains characters that need encoding.
- Otherwise it's a file: set headers (ETag, Last-Modified, Content-Length, Content-Type), `r->allow_ranges = 1`, send headers + the file via the output filter chain.

**`ngx_http_index_module.c` — directory → file.** One handler (`ngx_http_index_handler`, 185 LoC) also on CONTENT_PHASE, also runs only when the URI ends with `/` (line 112–114). For each configured index name:

- If the name is *absolute* (starts with `/`) and has no variables, `ngx_http_internal_redirect(r, &index[i].name, &r->args)` (line 135–137) — the name becomes the new URI and re-enters location matching.
- Else compute `<root><uri><name>` (`ngx_http_map_uri_to_path` + `ngx_memcpy`, line 162–178), `open_cached_file` with `test_only = 1`. On ENOENT, fall through to the next index. On other errors, 500 or 403.
- Between the first probe and subsequent ones, `ngx_http_index_test_dir` checks that the *directory itself* exists (line 242–250). This differentiates "index names missing" (403 per `ngx_http_index_error`) from "directory doesn't exist" (404).
- On hit: `ngx_http_internal_redirect(r, &uri, &r->args)` with `uri = <request uri><index name>` (line 277).
- Merge rule (`ngx_http_index_merge_loc_conf`, line 405–439): child list, if non-null, replaces parent's. If both empty, default to `["index.html"]`.

**`ngx_http_try_files_module.c` — probe-then-rewrite.** One handler on `NGX_HTTP_PRECONTENT_PHASE` (try_files_module.c:395–396) — note the phase is *earlier* than static/index, so a try_files match rewrites `r->uri` before those handlers run. For each probe except the last:

- Name ending with `/` and not the last arg → `test_dir = 1` (line 318–325).
- `open_cached_file` with `test_only = 1` (line 222). ENOENT/ENOTDIR → `continue`; match against `of.is_dir == test_dir` to confirm file-vs-dir (line 248–250).
- On hit: `r->uri = path` (the URI under root), then `NGX_DECLINED` (line 252–283). That lets the content phase re-dispatch under the new URI.

The last arg is the fallback:

- Starts with `=` → parse code, `return tf->code` (line 196–198 and 350–362).
- Starts with `@` → `ngx_http_named_location` (line 203–204).
- Else → `ngx_http_internal_redirect` with the URI (line 206–210).

### `src/http/modules/ngx_http_map_module.c` — `map $source $dest { ... }`

- **Two match surfaces, same block.** The parser splits entries into (a) an exact-string hash and (b) a declaration-ordered regex list (map_module.c:`ngx_http_map_find`). Exact lookups run first; the regex list runs only when no exact hit and is linear (short-circuits on first match). This is why exact-matches beat regex patterns even when both would apply.
- **`default` is optional.** Absent default ⇒ unmatched renders empty — nginx distinguishes this from an explicit `""` default only to the extent that the fallback vs. empty-string sites diverge elsewhere; for rendering purposes both produce the same bytes.
- **Values are complex values.** RHS may reference other `$vars`, including the source. Rendering happens lazily per request — maps are not pre-rendered at startup.
- **Rust mapping.** We fold the exact side into a `HashMap<Vec<u8>, &'static [PreparedValuePart]>` (nginx uses `ngx_hash_t`; the shape is the same), keep regex entries in declaration order with pre-compiled `regex::bytes::Regex`, and stash `default` as an `Option`. Dispatch lives in the `Variable::Unknown` render path right after `split_clients` — same architectural slot, different matching rule. Deferred: `ngx_http_geo_module` (IP-keyed sibling). `hostnames` and `volatile` are implemented since.
- **Caching.** nginx caches every cacheable variable in `r->variables` for the whole request, internal redirects included. ruxen caches only `map` results: the first one per map is kept in `RewriteState` (which already outlives internal redirects and is kept for the access log), unless the map is `volatile`. Other variables, `split_clients` included, are evaluated on each reference; that differs from nginx only when their inputs change mid-request, which `map` over `$uri` (`map_volatile.t`) is the known case of.

### `src/http/ngx_http_special_response.c` + `ngx_http_core_module.c` — `error_page`

- **Merge rule is pointer inheritance.** `ngx_http_core_merge_loc_conf` copies `prev->error_pages` only when the child pointer is null (core_module.c:3844–3845). That means repeated `error_page` directives at one scope accumulate, but any child scope with at least one entry replaces the parent list outright.
- **Parser shape:** `error_page status... [=NNN|=] target;` (core_module.c:4919–5031). The parser compiles the target as a complex value, so variables are legal, and pre-splits literal `/uri?args` forms once at config time.
- **Runtime dispatch lives in special-response handling.** `ngx_http_special_response_handler` checks the current location's `error_pages` before building the builtin error body (special_response.c:464–474). Default recursion policy is off: once an `error_page` reroute has fired, nginx suppresses a second pass unless `recursive_error_pages on` is configured.
- **Internal URI targets** call `ngx_http_internal_redirect(r, &uri, &args)` (special_response.c:617–631). `r->uri` and `r->args` are replaced, but `r->unparsed_uri` remains the original request line and `valid_unparsed_uri` is cleared (core_module.c:2559–2603). This is why `$request_uri` stays original while `$args` changes on an error-page reroute.
- **Named-location targets** call `ngx_http_named_location(r, &uri)` (special_response.c:633–635). That jumps straight to the prepared named location without rewriting `r->uri` or splitting args, which is why `$uri` / `$args` stay on the current request URI when `error_page ... @name` fires.
- **Absolute-URL targets** do not reroute; nginx synthesizes a fresh `Location` header and defaults the response code to 302 unless the explicit overwrite code is itself a redirect status (special_response.c:640–676).

**Rust mapping.** Nginx's three-module split isn't load-bearing for us — we have no filter chain, no general subrequest engine (`auth_request` runs its subrequest in the worker, `run_auth_subrequest`), no open_file_cache. We fold static + index + try_files into one `fs_resolve::resolve()` function returning an `Outcome` enum. Phases stay a name, not a dispatch table: `FindConfig` + `ResolveFsPath` + `Content`. Try_files runs first, then static/index; the hop budget lives in `phase::process` so all reroutes share one counter.

**Performance note.** Root containment is one `openat2(RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS)` from the root's dirfd (`fs_resolve`), which walks and checks the path in a single syscall. (It used to be `std::fs::canonicalize` on every served file, about six syscalls per request.) Under `disable_symlinks off`, nginx's default, a path that leaves the root (EXDEV) is opened a second time without `RESOLVE_BENEATH` when it has no `..` component: a symlink took it out, and nginx's plain `open()` follows symlinks anywhere (#254, so `html/phpmyadmin -> /usr/share/phpmyadmin` works). A `..` that climbs out (from a variable in `try_files` or `alias`) stays a 403, stricter than nginx. `alias` joins the location's remainder with one `/`, where nginx concatenates as written: `location /img { alias /data/img/; }` maps `/img../x` to `/data/img/../x` in nginx (the "alias traversal" misconfiguration), and `location /img/ { alias /data/img; }` maps `/img/x` to `/data/imgx`; ruxen stays in the directory and warns about such a pair at startup. `on` and `if_not_owner` refuse such symlinks as before. The common case is still one syscall. A `root` or `alias` with variables (#232) is rendered per request as `ngx_http_map_uri_to_path` does (in a regex location an `alias` is the whole path) and opened as that request's anchor, one `open` more; a NUL or a `..` component that a variable brought in is a 403, where nginx would follow the `..`. Literal roots don't take that path.

### `src/http/ngx_http_upstream.c` + `ngx_http_upstream_round_robin.c` + `ngx_http_modules/ngx_http_proxy_module.c` + `ngx_http_upstream_keepalive_module.c` — reverse proxy

**Five-phase upstream state machine** (`ngx_http_upstream.c`). Each phase is an event-driven step the runtime re-enters; the request keeps moving between read/write handlers as the kernel signals readiness. State per-attempt: `request_sent`, `response_received`, `header_sent`, the read buffer (`u->buffer`, lazy-alloc on first recv), parsed `headers_in`, and timing fields. Order:

1. **`init_request`** (line 581) — allocate request buffer, call `u->create_request()` (proxy module fills it with the request line + headers), set up read/write handlers. All validation before any I/O.
2. **`connect`** (1557) — LB `get_peer()` then non-blocking `connect()`. NGX_OK/AGAIN/DONE → arm send/process handlers; NGX_BUSY → no live peers (FT_NOLIVE fallover); NGX_DECLINED → LB error (FT_ERROR fallover).
3. **`send_request`** (2148) — write request body. ERROR → fallover; AGAIN → arm send_timeout; OK → mark `request_body_sent=1`, arm read_timeout, possibly call process_header inline if read ready.
4. **`process_header`** (2440) — read into `u->buffer`, call `u->process_header()` (proxy: parse status line, then headers). On parse error → FT_INVALID_HEADER fallover; on success → `send_response`.
5. **`send_response`** (3250) — write client response headers, then either buffered (event pipe) or non-buffered (process_non_buffered_*) body forwarding.

**Half-closed states.** After full request sent but before response: read_timeout governs. If read event fires while write pending → posted via `ngx_post_event`. On fallover mid-response → SSL clean shutdown, free peer FAILED, reconnect.

**Fallover boundary** (`ngx_http_upstream_next`, 4573). Continue to next peer **only if** `tries > 0` AND error type is in `next_upstream` bitmask AND not (idempotency violated: POST/PATCH after request already sent) AND `next_upstream_timeout` not exceeded. Else: map fault type to client status (TIMEOUT→504, ERROR→502, HTTP_500→500, etc.). Idempotent + body sent + non-idempotent method → mark FT_NON_IDEMPOTENT and stop.

**Round-robin LB** (`ngx_http_upstream_round_robin.c`). Three-function contract: `init_peer` (per-request setup, tried bitset), `get_peer` (select among eligible), `free_peer` (post-attempt accounting).

- **Eligibility filter** in `get_peer` (811): skip if already-tried, `peer->down`, or `fails >= max_fails && (now - checked) <= fail_timeout`, or `conns >= max_conns`.
- **Weighted RR via smoothed weights**: each peer carries `weight` (immutable config), `effective_weight` (gets penalized on failure, recovers up to `weight`), `current_weight` (per-round accumulator). Each call adds `effective_weight` into `current_weight`, picks max, deducts total weight from chosen.
- **`free_peer`** (1008): on PEER_FAILED, increment `fails` and decrement `effective_weight` by `weight/max_fails` (floor at 0). On success, reset `fails`. Recovery is automatic: peer becomes eligible again `fail_timeout` after the last check.

**Proxy module** (`ngx_http_proxy_module.c`).

- **`create_request`** (1176) builds the upstream wire bytes: `METHOD URI HTTP/<version>\r\nHost: ...\r\n[custom headers]\r\n\r\n[body]`. The Host header is computed from `proxy_pass`, **not** the client's Host (this is the canonical surprise — `$proxy_host` is the upstream's host:port, not the request's).
- **Default headers always overridden** (747–757): `Connection`, `Proxy-Connection`, `TE`, `Keep-Alive`, `Expect`, `Upgrade` are blanked (hop-by-hop; never forwarded). `Content-Length`/`Transfer-Encoding` recomputed from request body length / chunked flag. RFC 7230 §6.1 enumerates the canonical hop-by-hop set.
- **`process_status_line`** (1742) parses the response status; HTTP/1.0 response sets `headers_in.connection_close = 1`. **`process_header`** (1828) reuses the request-header parser in response mode and dispatches each header to handlers that mark semantically important ones (Content-Length, Connection, Transfer-Encoding).
- Directives → location conf: `proxy_pass` (parsed at config time, stored as upstream-block reference or literal host:port; with variables it is evaluated per request, and a host name then needs the resolver), `proxy_set_header` (compiled into a script, evaluated per-request), `proxy_pass_request_headers/body` (booleans), `proxy_http_version` (1.0/1.1), `proxy_*_timeout` (ms).

**Keepalive pool** (`ngx_http_upstream_keepalive_module.c`). Per-upstream-block queue of `{ connection, sockaddr }` items. Linear search by sockaddr (240–248). Lifecycle:

- **`get_keepalive_peer`** (205) wraps the LB's get_peer, then searches the cache for a connection matching the chosen peer's sockaddr. Hit → reset connection state, mark `pc->cached=1`, return NGX_DONE. Miss → use a fresh connection.
- **`free_keepalive_peer`** (278) decides whether to cache. **Don't cache** if: PEER_FAILED, EOF / error / timeout on either direction, `c->requests >= conf->requests`, age `> conf->time`, `!u->keepalive` (upstream said `Connection: close`), `!u->request_body_sent`, or graceful shutdown. Otherwise enqueue with idle timeout.
- **Defaults since 1.29.7.** Before it, `proxy_http_version 1.1` + `proxy_set_header Connection ""` + `keepalive N` was the recipe; without them the upstream got HTTP/1.0 with `Connection: close`. Now HTTP/1.1 with no `Connection` header is the default (`ngx_http_proxy_headers`), and every `upstream {}` block gets `keepalive 32 local` unless it says `keepalive 0;` (`ngx_http_upstream_keepalive_init_main_conf`; implicit upstreams are skipped). `local` (`get_keepalive_peer`: `item->tag != kp->upstream->conf`) hands a connection only to the location that cached it. `keepalive N` caps the whole upstream's cache, and a full cache drops its least recently used item, whichever peer it is for.

**How ruxen's proxy is built.**

- **Sync → async handoff.** `phase::process_with_meta` stays synchronous: a proxied location returns `Response::Proxy(ProxyPlan)`, everything the exchange needs (upstream, rendered headers, body, timeouts, cache plan). The connection task awaits `proxy::run_proxy(plan)` in `settle_proxy_response`, then the response takes the same path as any other: `proxy_redirect`, the range filter, `add_header` / `add_trailer` with `$upstream_*` filled in, gzip, the write and the access log. `proxy_intercept_errors` and `X-Accel-Redirect` come back as an internal reroute into `phase::process_with_meta_from_reroute`.
- **No event-driven recursion.** An attempt is one `async fn` (`proxy::attempt`) with awaits at connect, send and read, each under its own `proxy_*_timeout`; `run_proxy` is the loop over attempts. nginx's handler steps and `ngx_post_event` have no counterpart.
- **Load balancing** (`src/upstream.rs`): nginx's smoothed weighted round-robin, `least_conn`, `hash` and `ip_hash`. `pick_peer` returns a `LeasedPeer` guard that counts the peer's active requests until it drops, so the counts can't drift. Per-peer state (weights, the `max_fails` window) is thread-local, keyed on the leaked upstream, unless the upstream has a `zone` (below).
- **Failover** follows `ngx_http_upstream_next`: the attempt's failure kind (`error`, `timeout`, `invalid_header`, `http_*`) against `proxy_next_upstream`, `proxy_next_upstream_tries` and `_timeout`; a non-idempotent request that went out moves on only with `non_idempotent`. `upstream::Tried` is nginx's `rrp->tried`. A pooled connection that fails before the response head is retried once on a fresh one when the request may be sent again. Failed attempts are logged with nginx's wording; the happy path allocates nothing for them.
- **Keep-alive pool:** per worker, one queue per upstream, most recently used first, bounded by `keepalive` (for the upstream, as nginx, not per peer), `keepalive_timeout`, `keepalive_time` and `keepalive_requests`. A take looks for the peer, the TLS config the connection was opened with and, for a `local` pool (the default), the location (`PreparedProxy::pool_tag`, the address of the location's leaked `ProxyResponseRules`). A connection goes back only when both sides allow it (HTTP/1.1, no `Connection: close`, the body read to its end).
- **`Connection` to the upstream (#582):** none by default, as 1.29.7, except over HTTP/1.1 with no pool to take the connection back (`keepalive 0;`, a `proxy_pass` without an `upstream {}` block): there ruxen still sends `Connection: close`. With 1.29.7's empty header the backend keeps the connection, the proxy closes it after the response and holds the TIME_WAIT; under load nginx 1.30.6 filled its ephemeral port range that way and ran at 8.8% of 1.24 (bench/campaign-2026-10-21). With `close` the backend closes first.
- **Request:** the client's headers minus the hop-by-hop ones (`is_hop_by_hop`, plus the names `Connection` lists), `proxy_set_header` overrides rendered first, `Host` from `proxy_pass` (`$proxy_host`), `Content-Length` recomputed from the body actually forwarded. A body that spilled to a temp file is streamed from it, reopened per attempt.
- **Response:** `Content-Length`, chunked or close-delimited framing, bare-LF lines tolerated as nginx does; the client always gets `HTTP/1.1`. A body that came whole with the head is chunked decoded and sent with a length. Otherwise it is relayed as it arrives (#88, `proxy_stream.rs`), framed for the client by the worker, and the upstream connection goes back to the pool after it. gzip compresses a relayed body on the way (`ProxyStream::gzip`, the `Deflater` the static files use): no length then, chunked to HTTP/1.1, the close for HTTP/1.0. The range filter cuts one range from it (`ProxyStream::window`; several are a multipart response, which nginx builds only for a cached body); `add_trailer` makes it chunked, and the worker renders the trailers once it is out; a body in memory gets them after gzip too (`ProcessMeta::trailers_due`), as nginx's chunked filter runs after its gzip filter. Failover and interception are decided on the status line, before the body, which is dropped unread (#463).
- **`proxy_pass` with variables** (#100) is rendered and parsed per request, as `ngx_http_proxy_eval` and `ngx_http_upstream_init_request` do: an `upstream` block of that name (only for a URL without a port, as the block's name has none) or the implicit upstream of another location's `proxy_pass http://host:port` with the same host and port, else an IP literal or `unix:` path as the one peer, else a host name for the location's `resolver` (#133, below), and without one a 502 with nginx's `no resolver defined to resolve` line. Such a location gets a placeholder upstream at startup, one peer with `max_fails=0` and no keepalive, and the plan carries the request's own peers (`ProxyPlan::adhoc`), the way nginx makes a round-robin set per request (ngx_http_upstream_create_round_robin_peer); nothing per request is leaked. A `unix:` path from a URL is interned per worker, at most 1024 of them. A URI part is the whole upstream URI; there is no implicit `proxy_redirect default`, and an explicit one is an `[emerg]`.
- **`resolver`** (#133, `src/resolver.rs`) turns the host name of a `proxy_pass` with variables into addresses at run time, as nginx's ngx_resolver.c does for ngx_http_upstream_init_request. `run_proxy` resolves before the first try (after the cache lookup, as nginx), and the addresses become the request's peers, tried in turn with `proxy_next_upstream`; `proxy_next_upstream_tries` caps them and `proxy_next_upstream_timeout` starts after the answer. Each `resolver` directive is one `Resolver` (the scopes that inherit it share its cache, as they share nginx's `ngx_resolver_t`), and the cache and the queries are per worker, in a thread-local keyed by it. A name is asked for A and, unless `ipv6=off`, AAAA; requests waiting for the same name share one query task (`drive`), each waiting with its own `resolver_timeout`. Each new name goes to the next server; an unanswered query goes to the next one every 5 s; a truncated answer is asked again over TCP from the same server; CNAMEs are followed up to 50; answers are cached by their smallest TTL or `valid=`, errors aren't. The answer rules are nginx's, down to which combinations of A and AAAA answers win and which malformed responses are logged and ignored (the query then waits on). Differences on purpose: each query has a UDP socket of its own (a fresh source port per query, where nginx keeps one socket per server), the query task ends as soon as no request waits for it, and a worker keeps at most 4096 cached names per resolver. The response parser is a fuzz target (`dns_response`).
- **Path rewriting:** `proxy_pass http://up/path;` replaces the matched location prefix with `/path`; regex and named locations with a path are an `[emerg]`, as `ngx_http_proxy_pass` refuses them.
- **A client that goes away** while the upstream is awaited (#136) ends the exchange, as `ngx_http_upstream_check_broken_connection` does: the proxy future is dropped, and with it the upstream connection; the error log gets nginx's `[info]` line, the access log a 499 with the attempt's times up to the close (its state is kept in place from the start), and nothing is sent. `proxy_ignore_client_abort on` keeps the exchange. The watch costs a fast exchange nothing: `client_watch::Watched` polls the proxy future and, once it waits, takes a ticket from a per-worker registry; one ticker per worker counts 100 ms ticks while any exchange waits, and only an exchange that has waited one to two ticks reads its client (`ConnIo::peer_closed`). Two things measured: a timer per request cost `proxy_hello` 4.7%, and a `settle_proxy_response` generic over the transport, or a `select`-style closure that grew the connection's future by 256 bytes, cost 2.5% and 1%; hence the trait object and the hand-written future. Subrequests (`auth_request`, `post_action`) aren't watched.
- **HTTPS upstreams** (#116): the connection to a peer is an `UpstreamIo`, plain TCP or TLS over it (`TlsStream<TcpStream, ClientConnection>`, the server's stream with the client side of rustls), through the attempt, the pool (keyed on TLS too), a relayed body and the tunnel after a 101 (TLS shared by both directions, as the client's is). The handshake runs under its own `proxy_connect_timeout` and fails like a connect, so `proxy_next_upstream error` moves on. nginx's defaults: no SNI unless `proxy_ssl_server_name on`, the name `proxy_ssl_name` or the `proxy_pass` host, sessions reused through one rustls `ClientConfig` per combination of settings (`upstream_tls::client_config`), and no certificate check: `NoVerification` takes any certificate and its handshake signature, which without a verified certificate proves nothing, and webpki would refuse the X.509 v1 certificates OpenSSL takes. `proxy_ssl_ciphers` is ignored as `ssl_ciphers` is.
- **Upstream certificate verification** (#117): `proxy_ssl_verify on` checks the chain as nginx's OpenSSL does, with the X.509 code of the AWS-LC that rustls already links (`x509_verify`, through `aws-lc-sys`): X509_verify_cert against `proxy_ssl_trusted_certificate` under the `ssl_server` purpose, OpenSSL's `proxy_ssl_verify_depth` (intermediates below the trusted certificate: 0 takes a leaf the trusted CA signed), `proxy_ssl_crl` with CRL_CHECK_ALL, a callback that lets the chain be checked to the end so the result is SSL_get_verify_result's, then X509_check_host on the name (subjectAltName DNS entries, the commonName without them). An address also matches an iPAddress entry, as later nginx checks addresses. webpki can't stand in for this: it refuses the self-signed CA:TRUE leaf `openssl req -x509` makes and X.509 v1, has no commonName fallback, and counts depth differently. The handshake signature is checked against the key of the verified certificate, taken from it by AWS-LC (webpki can't parse every such certificate) and checked by webpki from the bare key. A refusal fails the handshake like any other, with nginx's `upstream SSL certificate verify error: (N:text)` or `does not match "name"` in the log. A trust store is shared by every location whose files have the same content, and one `ClientConfig` per store and settings keeps sessions per verification.
- **Client certificates to upstreams** (#138): `proxy_ssl_certificate` / `proxy_ssl_certificate_key` load once per content of the files (`upstream_tls::client_certificate`) into the location's `ClientConfig`, whose resolver offers the one certificate when the server asks for one, as OpenSSL does. The config is part of the pool key and holds the session cache, so neither a pooled connection nor a session crosses identities. `""` cancels an inherited certificate. Paths with variables (#434), which nginx renders per connection, are rendered per request: an empty certificate means none, and otherwise the pair's files are read for each request, as nginx reads them per connection, or taken from `proxy_ssl_certificate_cache` (#601, `upstream_tls::ObjectCache`: certificates and keys by file, LRU with nginx's `max` / `inactive` / `valid` and its expiry order, re-read when inode or mtime changed, encrypted keys never kept; one per declaration, shared by the worker threads, where nginx has one per process). A key that doesn't match its certificate has both fetched again past the cache, as `ngx_ssl_connection_certificate` retries. A pair of the same content gets the same `CertifiedKey` and `ClientConfig` back (`certified_pair`, `client_config`; the location keeps its last 64 configs alive), so pooled connections and sessions still don't cross identities. A pair that doesn't load is a 500 with nginx's error-log line. `data:` values are refused.
- **Not yet:** `proxy_request_buffering off` (#134), client certificates with variables in the path, HTTP/2 and gRPC upstreams (#144), `mirror`.

**`hash` / `ip_hash` (#97).** `upstream::Lb` carries the prepared method; `Lb::Hash` holds the key and, for `consistent`, the ring built at startup (`160 × weight` crc32 points per primary server from its `server` text, sorted, read-only for all workers). The per-request state that nginx keeps in its peer data (running hash, rehash count, ring position, tries) is a boxed `HashPick` on `ProxyPlan`, built with the plan, so `proxy_next_upstream` picks continue where the first stopped. The mapping is nginx's bit for bit (golden tests in `upstream.rs`, checked against 1.24.0 on 625 keys and addresses): non-consistent `crc32([REHASH] KEY) >> 16 & 0x7fff` accumulated and walked by weight; `ip_hash` over three octets of IPv4 or sixteen of IPv6 (realip-aware, from `$remote_addr`); 20 tries, an empty key or one server fall back to round-robin. `backup` servers listed before the method stay out of the hash and serve only that fallback; after it they are refused. Failure state stays per worker, as nginx without `zone`.

**`zone` and `max_conns=` (#143).** `max_conns=N` caps a peer's requests in progress (`peer_eligible`), per worker as nginx's per process when the upstream has no `zone`. With `zone name [size]`, `PreparedUpstream.shared` holds one cache-line slot per peer (`upstream::PeerShared`): the connection count and the failure window are atomics every worker reads and updates, so `max_conns`, `least_conn` and `max_fails` see the whole process. The smoothed round-robin weights stay per worker instead of nginx's lock around each pick: proportions and health decisions are global, only the interleaving of picks across workers differs. Workers are threads, so the zone size only gets nginx's validation; several upstreams may name one zone, each keeping its own slots.

**Upgraded connections (#87).** An upstream 101 to a client that sent `Upgrade` (noticed while the client headers are forwarded, so it costs nothing more per request) ends `proxy::attempt` with `Response::Upgrade`: the head as nginx's header filter writes it (`Connection: upgrade`, the upstream's `Upgrade` kept, `add_header … always` applied) and the upstream connection with whatever it sent past the head. The connection loop writes the head and hands both connections to `worker::run_tunnel`, then logs and closes. The two directions run at once, each on a half of both connections (`duplex`, #501): a half keeps a raw pointer to the stream, and a `Duplex` operation makes a reference from it only between awaits, never across one, so the two directions never hold a `&mut` to one stream at once. A `Duplex` TLS read doesn't flush records rustls queued (alerts, KeyUpdate replies): only writes put records on the socket, and they drain the queue until it is empty. The halves run under Miri over an in-memory stream (`cargo +nightly miri test --bin ruxen -- duplex poll_io`); TLS can't, aws-lc-rs being C. Timeouts are nginx's (`proxy_read_timeout` without traffic either way ends it with `upstream timed out … while proxying upgraded connection`; `proxy_send_timeout` / `send_timeout` per write). After a reload a tunnel lives until `worker_shutdown_timeout`, as on an old nginx worker. A 101 the client didn't ask for goes out as a bodiless response and its connection is never pooled. nginx reads a close-delimited body after it instead (`ngx_http_proxy_input_filter_init`: "no 1xx since we don't send Expect and Upgrade"); dropping the bytes is the safer choice. Bytes after a bodiless head are no longer forwarded. The peer stays leased while a tunnel is open, so `least_conn` counts it, and the read timeout pauses while a write waits for its peer, as nginx's read timer does.

**Early hints from the upstream (#581).** A 103 head is interim, as in nginx 1.29.0+ with `early_hints` unset: `proxy::attempt` checks its header lines like any head's, drops it from the front of the header buffer and reads the next status line, from the bytes already read or the next read, for as many 103s as come. A 103 in an HTTP/1.0 response is an invalid header (`upstream sent HTTP/1.0 response with early hints`: a 502, or `proxy_next_upstream invalid_header`). The common case pays one compare on the status code; the rest is in the cold `drop_early_hints`. `$upstream_status` is the final status, on purpose (decided 2026-10-22, #616): nginx 1.30.6 logs the 103, because it sets `u->state->status` from the first status line only, which reads as an oversight against its own documentation ("the status of the response obtained from the upstream server"). Forwarding the hints (the `early_hints` directive) isn't implemented. Other 1xx (100, 102, a 101 the client didn't ask for) are still final responses, as in nginx.

**`proxy_bind` (#135).** A request's local address is resolved in the handler (`resolve_bind`: literal parsed at prepare, otherwise rendered; empty binds nothing, garbage is nginx's `invalid local address` and binds nothing) and rides on `ProxyPlan.bind`. A fresh connection with a bind goes through `proxy::connect_bound` instead of monoio's io_uring connect: a socket2 socket gets `IP_TRANSPARENT` when asked and `IP_BIND_ADDRESS_NO_PORT` when no port is given, is bound, connects non-blocking and is handed to monoio, which waits for it to become writable and reads `SO_ERROR`. Failures before connect() are the request's, as in `ngx_event_connect_peer`: a 500 with nginx's `[crit] bind(…) failed` / `[alert] setsockopt(IP_TRANSPARENT) failed`, the peer not blamed. A UNIX-domain peer with a bind fails the same way (nginx's bind() gets EINVAL there). Pooled connections are reused whatever address they were bound to, as nginx's keepalive cache does.

## HTTP/2 (#144)

`worker::h2` serves HTTP/2 clients with the `h2` crate, as the runtime decision (#272) allowed, instead of nginx's own `ngx_http_v2.c`. A connection is HTTP/2 when its address has HTTP/2 on and either TLS negotiated `h2` through ALPN or a plain connection starts with the client preface (looked at with `MSG_PEEK`, so HTTP/1.1 goes on untouched when it doesn't).

- **The crate on monoio.** `h2` drives its connection through tokio's poll-style `AsyncRead` / `AsyncWrite` (the traits only: no tokio runtime). `h2::compat::PollIo` owns the monoio stream and runs one rent-style read and one write at a time as boxed futures, with buffers of its own. They run on the stream's two `duplex` halves, as a WebSocket tunnel's do.
- **A stream is a one-request HTTP/1.1 connection.** Each stream runs `handle` with a `StreamIo` as its connection: reading gives the request as an HTTP/1.1 head whose version is `HTTP/2.0` (which the parser accepts only there, `ParseState::h2`; `$server_protocol` and `$request` show it), `Host` from `:authority` (a client `Host` that isn't the same bytes is refused with 400, as nginx does since 1.29.1, #592), the `cookie` fields joined, and the DATA frames as the body (chunked when there is no Content-Length); writing parses the response `handle` writes back into a HEADERS frame (connection-specific fields dropped) and DATA frames, sent as the flow-control windows allow, and decodes a chunked body on the way. So rewrites, static files, the proxy, `error_page`, access control and logging work on HTTP/2 without a second implementation. A response cut short (or none, `return 444`) resets the stream. `$connection_requests` and `$connection_time` count per connection (`ConnIo::conn_counters`).
- **Header limits** (#623): `large_client_header_buffers` of the default server bounds each name and value (`size`) and all of them together, pseudo-headers included (`size × number`), checked as a stream arrives (`h2::fields_over_limit`); over them the connection ends with GOAWAY ENHANCE_YOUR_CALM and nginx's `client sent too large header field` / `too large header` at `info` (ngx_http_v2_state_field_len, ngx_http_v2_state_process_header). nginx compares a Huffman-coded string's length as sent, ruxen the decoded length. The rebuilt HTTP/1.1 head isn't checked line by line (its joined `Cookie` may be longer than `size`); it grows up to the crate's bound, `max_header_list_size`: twice the total, at least 64 KiB, since the crate counts 32 bytes per field on top and would answer 431 first.
- **What nginx announces:** 128 concurrent streams, a 64 KiB stream window (`http2_body_preread_size`), the largest frame size, and a WINDOW_UPDATE that opens the connection window to 2^31−1 (`ngx_http_v2_send_settings`, `ngx_http_v2_init`). The decoded request head is bounded by `large_client_header_buffers` (below).
- **Settings** (#346): `http2_max_concurrent_streams` and `http2_body_preread_size` (the stream window), at http and server level, taken from the address's default server as nginx does. `http2_chunk_size` (the largest DATA frame, nginx's 8k by default) is a location setting as in nginx (#594): it rides in the location's `PreparedClientTimeouts` next to `send_timeout`, and `handle` gives it to the stream once the request has a location (the final one, after internal redirects, as ngx_http_v2_send_chain reads it); until then the default server's applies. The obsolete `http2_*` directives (the old timeouts and limits, server push; the push ones in a location too) are accepted with nginx ≥ 1.25.1's warning; `http2_recv_buffer_size`, `http2_pool_size` and `http2_streams_index_size` tune nginx's own allocator and change nothing here.
- **Per server.** `http2 on|off` (http, server) and `listen … http2` (the address). ALPN offers `h2` by the server the SNI name selects (`phase::tls_choice`, through the ClientHello-first accept that `ssl_reject_handshake` uses, only where the servers differ); a plain connection is looked at when `listen … http2` or the default server has it on; a request whose `Host` names a server with HTTP/2 off gets 421, as `ngx_http_set_virtual_server` does.
- **Lifecycle:** the default server's `keepalive_requests`, `keepalive_time` and `keepalive_timeout` (0: GOAWAY after the streams) end a connection with GOAWAY; before its first stream, `client_header_timeout` from the accept bounds it instead (`ngx_http_v2_init`); so do a shutdown and a reload, the streams in progress finishing. The connection then closes with a lingering close (`lingering_close`), as nginx does: what the client still sends (a WINDOW_UPDATE, a PING) would make the kernel reset it and lose the end of a response.
- **Reset streams (CVE-2023-44487, "rapid reset").** A client's RST_STREAM closes a stream in the crate at once, so the crate's `max_concurrent_streams` alone doesn't bound the work behind reset streams: one connection could run keepalive_requests upstream requests at once. So a stream counts against `http2_max_concurrent_streams` until its task ends, as nginx counts `h2c->processing` until the request ends; with every slot busy the connection is driven without accepting (`poll_closed`), and new streams wait in the crate, which keeps at most `max_concurrent_streams` open and sends GOAWAY ENHANCE_YOUR_CALM once 20 waiting ones are reset. nginx refuses a stream over the limit (REFUSED_STREAM, ngx_http_v2_state_headers) instead: waiting doesn't refuse one a client opens as the previous response ends, a moment before its task does. And a reset ends the work: it is the stream's `peer_closed`, so a proxied exchange ends with 499 unless `proxy_ignore_client_abort` is on, as ngx_http_v2_state_rst_stream sets `fc->error`; it is looked at once the upstream has kept the exchange waiting a tick or two, as an HTTP/1.1 close is (#136), and a response being written ends at its next write.
- **Where it differs from nginx, on purpose** (decided 2026-10-21, #347): ruxen keeps the crate's RFC 9113 / RFC 7541 behaviour where nginx is more lenient or answers otherwise. A malformed request (an invalid or empty `:authority` or `:method`, a connection-specific field, a regular field before a pseudo-header, a field name with characters the RFC forbids, a value with control characters (the `http` crate's `HeaderValue` refuses all but tab, where RFC 9113 forbids only NUL, CR and LF), a body longer or shorter than its Content-Length) is a stream error (RST_STREAM PROTOCOL_ERROR), where nginx answers some with 400 and serves others; HPACK errors get the RFC's GOAWAY codes (PROTOCOL_ERROR where nginx says COMPRESSION_ERROR or FRAME_SIZE_ERROR); Huffman padding longer than 7 bits is refused (RFC 7541 §5.2; nginx takes up to 29 bits); response fields are always Huffman-coded; a graceful GOAWAY first carries the last stream id 2^31−1 and a PING, the final one after the client's PONG, where nginx sends one with the last stream id; priorities are ignored; WINDOW_UPDATEs for request bodies come at half the window. ruxen is a drop-in replacement, and real clients don't depend on any of these; the nginx-tests checks of them are marked in `NGINX_TEST_PROGRESS.md` (`scripts/_render_test_progress.py`, `NOTES`). Server push isn't implemented (nginx removed it in 1.25.1).
- **`-V`** claims `--with-http_v2_module` (#395), so nginx-tests' HTTP/2 files run.
- **Performance:** against nginx 1.24.0 with `h2load` (ABBA on the i7): `h2c_hello` 165.5%, `h2_tls_hello` 150.1%, `h2c_static_8k` 108.3%. The writes that got there: `PollIo` writes vectored and double-buffers, so a response's frames leave in one write, and file bodies on a stream are read straight into DATA frames (`ConnIo::send_file_body`). HTTP/1.1 pays a flag check per connection on addresses with HTTP/2 (a `MSG_PEEK` on plain ones) and nothing elsewhere; `handle` gets a third instance for `StreamIo`.

## gzip (#93)

`worker::gzip` is nginx's `ngx_http_gzip_filter_module` plus the core module's `ngx_http_gzip_ok`. It runs once per response in the worker, after the location, `error_page` and the proxy have settled it, and only where `gzip on` (`ProcessMeta::gzip`, `None` otherwise: one check per response).

- **Decision:** the order of nginx's header filter. Status 200/403/404, no `Content-Encoding`, `Content-Length` ≥ `gzip_min_length`, a type in `gzip_types` (`text/html` always). Then `Vary` is set, and `ngx_http_gzip_ok` decides: `Accept-Encoding` with nginx's token and q-value rules, `gzip_http_version`, `gzip_proxied` for requests with `Via`, and `gzip_disable`.
- **Bodies in memory** (`return`, error pages, proxied responses, small files) are compressed whole and keep a `Content-Length`. nginx sends them chunked; a length is equally valid, and it lets HTTP/1.0 clients keep the connection.
- **Files** are compressed as they are sent (`stream_file_gzip`, 64 KiB blocks): chunked for HTTP/1.1, and with a close after the body for HTTP/1.0. They leave the `sendfile` path, as in nginx.
- **Ranges:** nginx's range filter runs after gzip and finds no length. So a file gzip would compress is sent whole, with a 200, whatever the `Range`; the static handler asks `gzip::would_compress` before it cuts one.
- **Compression:** zlib-rs, pure Rust like rustls, used directly. flate2 would hide `memLevel`, which shrinks with the window as in `ngx_http_gzip_filter_memory` (window bits for short known lengths; an 8 KiB page gets 14 and memLevel 7). Files up to 64 KiB are read and compressed whole, so the header and body go out in one write.
- **Allocation:** deflate states and the stream's buffers are pooled per worker and only reset. A fresh deflate state is a few hundred KiB, and glibc maps and unmaps blocks that size per response. The 64 KiB stream buffers made the thread arenas trim their top pages and fault them back in. Together that was 1.2 M page faults in 3 s and half of nginx's throughput on `gzip_html_8k`. nginx takes the same memory from the request pool. zlib-rs runs level 1 as `deflate_quick`, whose output is far larger than zlib's level 1 (8 KiB HTML +30 %, 2 MiB CSS +82 %). nginx's `gzip_comp_level 1` therefore maps to zlib-rs level 2, which matches zlib's level 1 in size.

## Proxy cache (#233)

`proxy_cache.rs` is nginx's file cache (`ngx_http_file_cache.c`) without the manager and loader: store a response, serve it while fresh, revalidate it, answer from it when stale.

- **Index:** a `proxy_cache_path` zone is a heap value all workers reach through `&'static`, 16 shards of a `Mutex` around a map and an LRU list, like the `limit_req` zones. A node holds what nginx's `ngx_http_file_cache_node_t` holds for step 1: uses, `valid_sec`, the status of a cached intercepted error, whether a file exists, and its size. Capacity is the zone size / 128, fixed; a full shard drops its least recently used node and that node's file, and sets the zone's watermark at 7/8 of the entries it holds (nginx's `ngx_http_file_cache_set_watermark`). `inactive` is checked on lookup, and a thread per zone does the rest of nginx's loader and manager: at startup it indexes the files already there (and removes leftover temp files), then passes as nginx's `ngx_http_file_cache_manager` does (#839): inactive entries go, then the zone's least recently used (the oldest of the shards' oldest) while over `max_size`, at the watermark or under `min_free`; at most `manager_files` entries or `manager_threshold` of work per pass, then `manager_sleep`, else until the next entry would turn inactive (at most 10 s). Over `max_size` the cache stays until that pass, as in nginx. A pass that panics is logged (`alert`) and the next one runs, as nginx's master respawns its cache manager (#524); a thread that can't be started is logged too, and the next reload tries again. The `loader_*` knobs are checked and unused. Until the loader has seen a file, a lookup the index doesn't know reads it from disk (nginx's cold cache).
- **Files** are ruxen's format, not nginx's (a cache directory isn't shared with nginx): a fixed header with `valid_sec`, the key, the `Vary` value and the request's digest over the headers it names, the upstream's header block, then the decoded body. Names are hex of a SHA-256 prefix of the key, spread over `levels` as nginx spreads its md5 names; the stored key guards against a collision. Writes go to a temp file in the cache directory and are renamed into place (`use_temp_path` is accepted either way). They are blocking writes on the worker thread, as nginx's are without `aio threads`. A relayed response is written as it goes (`CacheFill`, nginx's cacheable pipe, #463): the body's length goes into the header once it is complete, and the update lock is held until then. When the client goes away, gets a 304 from the not-modified filter, or asked with HEAD, a detached task reads the rest into the file.
- **Hits** go through `run_proxy` like a fresh response: the stored upstream header passes the same filter (`client_head`: hidden headers, `proxy_pass_header`, X-Accel-*, `$upstream_http_*`), then `proxy_intercept_errors`, `proxy_redirect` and `add_header` as usual. The body is sent from the file (#515); with `add_trailer` it goes chunked, the trailers after it (#793).
- **Freshness** reads the headers in order, as nginx's header handlers do: `X-Accel-Expires` wins over `Cache-Control`, which wins over `Expires`; `no-cache`, `no-store`, `private`, `max-age=0`, `Set-Cookie` and `Vary: *` keep a response out; `proxy_ignore_headers` drops any of them. Without a lifetime from the headers, `proxy_cache_valid` decides.
- **Vary**, as nginx: a response with `Vary` is stored at the main key, and a request with other values of the headers it names looks at its own variant's key (`ngx_http_file_cache_reopen`), where its response is kept; one that comes with another `Vary`, or none, replaces the main key's (`ngx_http_file_cache_update_variant`).
- **Revalidation** (`proxy_cache_revalidate`): a stale 200 or 206 asks again with its `Last-Modified` and `ETag`. A 304 answers from the stale entry (`REVALIDATED`) and renews it for the 304's lifetime, else the one the stored headers give from now, else `proxy_cache_valid`'s. The new `valid_sec` is written into the file in place.
- **Stale responses and locks** use nginx's `updating` flag on the node, held by one request through a token and released when its `CachePlan` is dropped, whatever the outcome. A stale lookup makes the first request the updater (STALE); later ones find it held (UPDATING) and answer from the stale file if `proxy_cache_use_stale updating` or the response's `stale-while-revalidate` allows. `proxy_cache_background_update` sends the stale response and moves the request's plan into a spawned task that fetches and stores the new one, like nginx's background subrequest. An upstream failure or a status `proxy_cache_use_stale` lists (or `stale-if-error`) answers from the stale file. `proxy_cache_lock` takes the same flag for a missing response; the others sleep in `run_proxy`, looking again at most every 500 ms, until the response is cached, the lock is released or older than `proxy_cache_lock_age`, or `proxy_cache_lock_timeout` ends (then they fetch without storing).
- **Requests:** once `proxy_cache_min_uses` is reached (nginx's `u->cacheable`), the conditional and range request headers aren't sent upstream (`ngx_http_proxy_cache_headers`); below it they are. A HEAD goes up as a GET (`proxy_cache_convert_head`). With `proxy_cache_convert_head off` it goes up as a HEAD, and its answer is stored without a body, as nginx stores it: a GET that hits it gets the head with its `Content-Length` and no body (`proxy_cache_convert_head.t` 3–4). nginx then keeps the connection, and the client takes the next response for the body; ruxen closes it. A cache key with `$request_method` is nginx's own advice for this setting. `proxy_no_cache` is rendered before the request goes upstream, so `$upstream_http_*` in it read nothing; nginx renders it after the response header.

## Byte ranges

- **Static files** (`file.rs`, #401) use the range filter's parse (`worker::range::parse_header`, up to `max_ranges`; `max_ranges 0` turns ranges off) and `If-Range` against the ETag or `Last-Modified`. One range is a 206 with `Content-Range` whose body is the file slice, inline or as a `FileBody` (sendfile), and no `Accept-Ranges`, as nginx's. Several are a `multipart/byteranges` 206 built by `worker::range::multipart` with the parts `pread` from the file; up to 1 MiB in total (`MULTIPART_MAX`), beyond which the file goes whole as a 200, where nginx streams the parts from the file. None satisfiable is nginx's 416 page (`worker::range::not_satisfiable`).
- **Proxied and cached responses** (#370) go through `worker::range`, nginx's range filter over a response held in memory: nginx's range parse, one range as a 206 with the filter's own `Content-Range`, several as `multipart/byteranges` (a counter boundary, nginx's part layout), none satisfiable as nginx's 416 page with `Content-Range: bytes */<length>`. When it may cut follows `ngx_http_upstream_process_headers` and `ngx_http_upstream_copy_allow_ranges`: `proxy_force_ranges` (one range; several on a cache hit), an upstream `Accept-Ranges` on a cache hit (several) or on a cacheable response (one). The upstream's `Accept-Ranges` is dropped then and the filter writes its own; otherwise the response goes out as the upstream sent it. A body without a length (chunked) is never cut. The filter runs before `add_header` / `add_trailer` and skips a response gzip will compress, which is nginx's order: gzip, then the range filter, then the chunked filter that writes the trailers.

## Static file bodies and `sendfile`

`sendfile on|off` (http / server / location, default off as in nginx) picks how file bodies leave the process. Measured on static_8k (8 KiB, `wrk -t16 -c512`): the copying path was at 89% of nginx; with sendfile on both servers ruxen is at ~96.5%.

- **`sendfile off`** (and a TLS connection in userspace): bodies up to 8 KiB are `pread` into the response buffer and written with one io_uring write; larger bodies stream through a 64 KiB buffer (`stream_file`). Two user-space copies per body byte.
- **`sendfile on`, plain TCP, body ≥ 4 KiB**: `serve_path` returns `Response::File` and the worker calls `send_head_and_file`. The header block goes out with `send(MSG_MORE)` so the kernel coalesces it with the first file pages (nginx gets the same from `tcp_nopush`). The body goes out with `sendfile(2)` in ≤ 2 MiB chunks (`sendfile_max_chunk` default). No user-space copy.
- **Non-blocking without a new io_uring op.** monoio's `Pipe` doesn't expose its fds, so io_uring `splice` isn't reachable from outside the crate. Instead the socket is switched to `O_NONBLOCK` on first use and `send`/`sendfile` are called directly; on `EAGAIN` the worker awaits `TcpStream::writable()` (an io_uring PollAdd). io_uring ops on the same socket behave the same with or without the flag, because the kernel already tries non-blocking first and arms a poll on EAGAIN. `tests/m45_sendfile.rs` checks that a stalled reader doesn't block the worker.
- **Why 4 KiB.** Below it, `pread` + one io_uring write beats two direct syscalls: against the inline path, 1 KiB was −3%, 2 KiB break-even, 4 KiB +6%, 8 KiB +8%. nginx itself uses sendfile for every size.
- **File side is synchronous**, like the `pread` it replaces: a page-cache miss blocks the worker for the disk read. nginx has the same property without `aio`.
- **kTLS** (`ssl_conf_command Options KTLS`, #673; `src/ktls.rs`): rustls runs the handshake, then hands its traffic keys to the kernel (`dangerous_extract_secrets`, `setsockopt(SOL_TLS)`), and the connection goes on as a `KtlsStream`: plaintext reads and writes and `sendfile` on the socket, as plain TCP. The switch needs the record boundary: ciphertext rustls was given is tracked by record header (`RecordCursor`), and a read that ends mid-record keeps the connection in userspace. Also in userspace: a cipher or version the kernel lacks (`probe`, once at startup, as root, which loads the `tls` module). Non-data records come as `EIO` on a read, then `recvmsg` with a control buffer: close_notify is EOF, a TLS 1.3 KeyUpdate is taken (#852), anything else closes. Key updates: the buffered rustls API has no `KernelConnection`, so the kTLS configs log the application traffic secrets (`KeyLog`, `ktls::SecretLog`, filed by ClientHello random, which the record cursor keeps), the switch checks them against the extracted keys, and `Rekey` derives the next generation (RFC 8446, 7.2) and sets it again with `TLS_RX` / `TLS_TX` (Linux 6.14+; older kernels refuse, and the connection closes). A requested update is answered with our KeyUpdate before more data; at 2^24 AES-GCM records the server updates its own key (TLS 1.2 closes there). TLS 1.2 AES-GCM: the kernel counts explicit nonces up from the one it is given, rustls XORs the sequence in, so the kernel's start is moved half the range away.

## TLS architecture

Server-side HTTPS lives in `src/tls.rs` (handshake glue + post-handshake
snapshot), `src/tls_stream.rs` (rustls ↔ monoio stream adapter) and
`src/tls_certs.rs` (PEM loader + SNI resolver + `ServerConfig` builder). Wired into the worker accept loop via
`spawn_connection`, which branches on `PreparedListen::tls`.

- **rustls 0.23.** Pure-Rust API surface, no OpenSSL link,
  MIT/Apache-2.0. BoringSSL via `boring` would likely be faster on some
  workloads but adds a C build dep. Revisit only if HTTPS bench shows a
  >20% gap to nginx and profiling traces it to crypto rather than I/O.
  Crypto provider is rustls's default `aws-lc-rs`.
- **Own rustls ↔ monoio adapter (`src/tls_stream.rs`).** Until
  2026-10 this was the `monoio-rustls` crate. We needed the negotiated
  session (`get_ref`) for `HandshakeInfo`, upstream left the PR adding
  it unreviewed and has had no release since 0.4.0 (May 2024), and
  crates.io refuses a package whose build depends on a git
  `[patch]`. The adapter is server-only, ~250 lines, and keeps the
  state ruxen needs visible: the negotiated `ServerConnection` and the
  ciphertext buffered ahead of rustls (needed for a TLS keepalive idle
  wait). Ciphertext buffers are allocated on first use rather than as
  two zeroed 16 KiB blocks per connection; each write drains rustls's
  whole outgoing queue into one socket write (upstream wrote in 16 KiB
  pieces); `writev` encrypts all iovecs as one run of records.
  Throughput on `tls_hello` is unchanged (ABBA pairs vs the old
  adapter, 2026-10-02: 99–100%).
- **Per-listen `TlsAcceptor`, built once at startup.** `build_listen_tls`
  walks every `server {}` on a given listen address, loads each
  `ssl_certificate` / `ssl_certificate_key` pair into a
  `rustls::sign::CertifiedKey`, and registers it with a
  `ServerNameResolver` keyed on `server_name`. Cert load failure is a
  startup abort, not a runtime degradation: `prepare` returns it as an
  `[emerg]` (`cannot load certificate "…" with key "…": …`), and since
  `-t` runs `prepare` too, `-t` catches an unreadable PEM or a key that
  doesn't match its certificate, as `nginx -t` does.
  Listens with no `ssl;` get `tls: None` and pay one `Option::is_some`
  on the accept path.
- **SNI resolver mirrors the HTTP `match_server` ladder**, as nginx's
  `ngx_http_ssl_servername` uses the same lookup as `Host`: exact, then
  leading wildcard (`*.example.com` registered under suffix
  `example.com`), then the longest trailing wildcard (`www.example.*`),
  then `~regex` names in declaration order (compiled a second time for
  the resolver at startup; they run only for SNI names that miss the
  tables before them). A name that matches nothing gets the listen's
  default certificate. Multi-cert per server (RSA + ECDSA both registered under
  one name) is supported by storing `Vec<Arc<CertifiedKey>>` per slot
  and selecting via `SigningKey::choose_scheme` against the
  `ClientHello`'s announced signature schemes — first match wins, falls
  through to the first registered key on no match so rustls can produce
  a clean handshake alert instead of us silently aborting.
- **Handshake-time vs request-time allocations.** A `HandshakeInfo`
  snapshot is built once after `accept_with_timeout` returns and
  threaded through the request loop as `Option<&HandshakeInfo>`.
  Request-path renders of `$ssl_protocol` / `$ssl_cipher` /
  `$ssl_server_name` / `$ssl_session_reused` are struct-field reads, not
  virtual calls into rustls. SNI is lowercased once at handshake time so
  per-request `find_config` does byte-equal comparisons against
  pre-lowercased `server_name` tables.
- **`Conn<S>` generic for the request loop.** `pub trait ConnIo:
  AsyncReadRent + AsyncWriteRent` carries what differs per transport
  (`idle_wait`, `sendfile_fd`, `sends_file_bodies`, …; `Duplex` for the tunnel). The handler `fn handle<S: ConnIo>(…)` is
  monomorphized for `TcpStream`, `ServerTlsStream<TcpStream>` and an HTTP/2 stream (`StreamIo`).
  Between keep-alive requests both plain TCP and TLS submit the read
  itself, raced against the keep-alive deadline, shutdown, a reload and
  a drain (`ConnIo::idle_read`, `read_first_or_shutdown`): one io_uring
  operation per request instead of a readiness poll and then the read
  (#145). TLS reads ciphertext into its stream's own buffer, and the
  request read hands it to rustls without going back to the socket;
  input the stream already holds (left from the handshake, as TLS 1.3
  clients send the first request with Finished, or from a previous
  read: `TlsStream::has_buffered_input`) is used at once. When the
  connection is to close, the read is dropped, which cancels it
  (monoio's `async-cancel`; #426 replaced a `Canceller`, whose `HashSet`
  cost about 8% of `m1_hello`'s instructions). The direct read was worth
  1–2.5% on the TLS scenarios on the bench laptop (#430); the readiness
  poll it replaced had come in when TLS started enforcing the idle
  timeout.
- **The handshake runs under `client_header_timeout`.** As in nginx
  1.24, which has no separate handshake timeout: the default server's
  `client_header_timeout` (60 s unless set) is armed at accept, and a
  PROXY protocol header read on the same listen shares it.
  `ssl_handshake_timeout` (nginx 1.25.3+) is an unknown directive here.
- **Session resumption follows nginx's defaults.** `ssl_session_cache`
  is off unless configured; when on, it is one in-memory
  `ServerSessionMemoryCache` (4096 entries) shared by all workers, with
  `ssl_session_timeout` enforced on lookup. `ssl_session_tickets` is on
  by default. A `shared:` cache is kept across a reload, not a restart.
  0-RTT and OCSP checks of client certificates aren't implemented yet
  (README, Limitations).
- **Session ticket keys are nginx's (#140).** `tls_ticket::NginxTicketer`
  builds tickets in the layout OpenSSL uses for nginx's key callback
  (`key name | IV | AES-CBC | HMAC-SHA256`), so the key name is visible.
  Keys come from `ssl_session_ticket_key` files (48 or 80 bytes; the first
  encrypts, all decrypt), or rotate every `ssl_session_timeout` with
  `ssl_session_cache shared:…` (nginx ≥ 1.23.2: the previous key still
  decrypts, `ngx_ssl_rotate_ticket_keys`), or are one random key. Workers
  are threads, so one ticketer behind an `RwLock` replaces nginx's
  shared-memory copy. The sealed state is rustls's session encoding:
  tickets resume across ruxen instances sharing key files, not with nginx.
  `ExpiringTicketer` still wraps it to enforce the ticket age.
- **`ssl_reject_handshake` (#112).** On an address where a server has it
  on, the handshake starts with rustls's `Acceptor`: the ClientHello's SNI
  name picks the server with the HTTP routing ladder
  (`phase::rejects_handshake`; no name or no match: the address's TLS
  default server), and if that server rejects, a plaintext fatal
  `unrecognized_name` alert goes out before any certificate is chosen, as
  nginx's servername callback does. Otherwise the handshake continues
  with the address's one `ServerConfig`. Addresses without it keep the
  direct `ServerConnection` path. A rejecting default server needs no
  certificate; the other servers then need one or reject too
  (ngx_http_ssl_init).
- **Client certificates, `ssl_verify_client` (#113).** As in nginx the
  handshake never fails over the certificate (its verify callback always
  returns 1): `client_verify::RequestCertificate` asks for one with the
  subjects of `ssl_client_certificate` as the CA list, takes any chain,
  and checks only the handshake signature, the client's proof that it has
  the key. The chain is checked once after the handshake, resumed ones
  included, against the server's store (`x509_verify`, OpenSSL's rules:
  `ssl_client_certificate` + `ssl_trusted_certificate`, `ssl_verify_depth`,
  `ssl_crl`), and the result rides in `HandshakeInfo`. As in nginx ≥
  1.27.2, `on` / `optional` load with only `ssl_trusted_certificate`
  (#587): the CertificateRequest then has no CA names; 1.24's `[emerg]`
  for it is gone. Requests are refused
  where nginx refuses them (ngx_http_process_request): 495 for a
  certificate the server rejects (`optional_no_ca` lets through the errors
  of ngx_ssl_verify_error_optional), 496 for none with `on`, both sent as
  400 and closing the connection unless `error_page` takes them; and 421
  when the Host isn't the SNI name and names a verifying server
  (ngx_http_set_virtual_server). The context is per server: rustls keeps a
  verifier per `ServerConfig`, so a server with its own context gets a
  config built from the address's (`tls_certs::with_client_verifier`, the
  same resolver, session cache and ticket keys), picked by the SNI name in
  the ClientHello-first accept; a server without certificates of its own
  takes the default server's, as its name keeps the default's SSL_CTX in
  nginx. Sessions can't carry a verification across contexts: resumption
  needs the same SNI name, and the chain is checked again on every
  handshake. Not done: nginx removes the session of a refused handshake
  from its cache; here a resumed one is refused the same way again.
  The `$ssl_client_*` fields (#114) are printed from the leaf's DER, kept in
  `HandshakeInfo`, by AWS-LC's own printers (`x509_verify::print_field`:
  `PEM_write_bio_X509`, `X509_NAME_print_ex` with `XN_FLAG_RFC2253`,
  `X509_NAME_oneline`, `i2a_ASN1_INTEGER`, `ASN1_TIME_print`), so the text is
  OpenSSL's, escaping and attribute names included; the certificate is
  parsed only when such a variable is rendered.
- **OCSP stapling (#141)** follows ngx_event_openssl_stapling.c, with
  the OCSP code of the AWS-LC that rustls links (`ocsp`), as `x509_verify`
  checks chains. Each certificate of a server with `ssl_stapling on` gets
  an `ocsp::Stapling`, which the SNI resolver asks for the certificate of
  each handshake (`tls_certs::ServerKey`): a `CertifiedKey` carrying the
  response while it is valid, which rustls staples when the client asks
  (TLS 1.2 and 1.3). `ssl_stapling_file` is read at startup and stapled as
  it is, whatever it says. Otherwise the startup finds the issuer (the
  certificates after the leaf, then the store `ssl_trusted_certificate`
  makes) and the responder (`ssl_stapling_responder`, else the AIA URL,
  `http://` only, resolved then, as nginx resolves it without a
  `resolver`), and warns `"ssl_stapling" ignored, …` where nginx does.
  The first handshake starts a fetch and goes without, as in nginx: a
  GET with the base64 request, then OCSP_basic_verify (`OCSP_NOVERIFY`,
  or `OCSP_TRUSTOTHER` with `ssl_stapling_verify`), the CertID's status,
  OCSP_check_validity with 5 minutes of drift. A `good` response is
  stapled until its nextUpdate and fetched again 5 minutes before, at
  least hourly; after a failure in 5 minutes. Unlike nginx's worker
  processes, the workers share a `Stapling`, so one fetch serves them
  all. The fetch is a `spawn_contained` task of the worker whose handshake
  started it, so it can't outlive its generation's arena, and it takes an
  upstream connection slot as ngx_event_connect_peer does. Error lines
  are nginx's, context included (`while requesting certificate status,
  responder: …, peer: …, certificate: "…"`). The handshake cost is a lock
  to clone an `Arc`, for stapling certificates only. A server on several
  addresses staples once: `prepare` keeps the stapling certificates of a
  load by their files and settings.
- **`$ssl_session_id` is ruxen's id for the session, not the wire bytes.**
  rustls exposes neither the TLS 1.2 session ID nor the TLS 1.3 ticket.
  When the variable is used and the listen resumes sessions, a full
  handshake draws 32 random bytes. They are stored in the session as
  rustls resumption data (`set_resumption_data`), and a TLS 1.3
  resumption gets them back. The value is 64 hex digits, as nginx's, and
  stable across resumptions, which is what log correlation and sticky
  keys need. rustls 0.23 doesn't return the data for a resumed TLS 1.2
  session, so that one renders empty. Without the variable in the
  config, handshakes are unchanged.

## Open questions

- `bumpalo` vs. fixed per-connection buffers vs. both. Current: fixed per-connection `Vec<u8>` (8 KiB, one alloc per connection, reused for every keep-alive request). No arena needed yet — revisit when we have a module/handler system that wants short-lived per-request allocations.
- CPU pinning strategy. **Decided (2026-04-16): opt-in via `RUXEN_PIN=1`, using `monoio::utils::bind_to_cpu_set` (no `core_affinity` dep — it's just a portability shim over the same `sched_setaffinity` syscall).** Default off, matches nginx's default (`worker_processes auto` + no `worker_cpu_affinity`). When enabled on the i9-13900HX (8P × 2 SMT + 16E), the tested layout is 16 workers pinned to CPUs 0–15 (all P-core logical threads, SMT on): per monoio/glommio and TFB plaintext results, naïve 0..31 pinning costs tail latency because SO_REUSEPORT doesn't rebalance and E-core queues back up. On a *colocated* client bench the effect is mixed — p99 improves ~37% but throughput drops because wrk on E-cores becomes the bottleneck (measured 2026-04-16; the raw affinity-comparison numbers were not carried into the public repo). With a dedicated client machine, pinning should be a clean win on both axes.
